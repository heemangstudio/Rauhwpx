# site-api

Small Node service behind the website beta form, the desktop install counter, accounts, licenses and issue reports. Its one dependency is `pg`. Without `DATABASE_URL` it stores everything as files in one data directory; with it, everything but issue-report attachments lives in Postgres (see Data).

## Routes

- `POST /v1/waitlist` takes `{ email }` from the website's 체험 신청 form. The body is sent as `text/plain` so the cross-origin call needs no preflight. CORS is open, and each IP may submit 10 times per 10 minutes. Each email is stored once.
- `GET /v1/waitlist` lists signups for `Authorization: Bearer $RAU_WAITLIST_ADMIN_TOKEN`. Without that variable the list stays closed.
- `POST /v1/unique-installs` records the first launch of a desktop install. `desktop/unique-install.mjs` signs the ping with the shared key in `unique-installs.mjs`.
- `GET /v1/unique-installs` returns the public total, and `GET /unique-installs` renders it as a page.
- `POST /v1/downloads {platform, version}` counts a download start from the website (`navigator.sendBeacon`, `text/plain`, CORS open). `platform` is one of `mac-arm64`, `mac-x64`, `win-x64`, `win-arm64`, `linux-x64`; `version` is `latest` or `x.y.z[-tag]`. 30 per IP per 10 minutes in memory. `downloads.json` keeps counts only, by KST day and `platform|version` (64 pairs a day, 400 days); no IP, user agent or identifier is stored. `GET /v1/admin/downloads?days=30` (`ADMIN_TOKEN`) and `license-admin.mjs downloads [--days N]` read them.
- `POST /v1/feedback` takes a desktop 문제 보고 (wire contract v1 in `feedback.mjs`): message, optional reply email, meta, diagnostic log, screenshot, chat and document, at most 40 MiB of JSON. `proof` is hex HMAC-SHA256 with the shared key in `feedback.mjs` over `${installId}\n${createdAt}\n${sha256hex(message)}`, and `createdAt` must be within 24 hours of server time. Answers `201 {ok, id}`, or `{ok:false, error}` with 400 `invalid` (plus `field`), 401 `bad_proof`, 413 `too_large`, 429 `rate_limited` (5 per install, 20 per IP per hour, checked before the body is read), 503 `busy` (3 uploads already in flight) and 507 `storage_full`. Each report pings the waitlist Telegram chat.
- `GET /v1/admin/feedback` lists reports newest first with status counts and storage use; `GET /v1/admin/feedback/report?id=` returns one; `GET /v1/admin/feedback/attachment?id=&name=screenshot|log|chat|document` returns a stored file; `POST /v1/admin/feedback/status {id, status: new|seen|resolved}` and `POST /v1/admin/feedback/delete {id}` change it. All need `ADMIN_TOKEN`.
- `GET /healthz`, `GET /rau.png` and `GET /favicon.ico`.

### License keys (HamaEditor on Groble)

Five kinds of Groble products can issue keys. The paused one-time product (`GROBLE_ONETIME_PRODUCT_IDS`, default `uRshdR`) still issues a **lifetime** key with no edition, so a refund of an old order keeps working. The 12-month auto-renewing subscription (`GROBLE_SUBSCRIPTION_PRODUCT_IDS`, default `GLJFC9`, ₩9,900) issues an **annual** key with `expiresAt`. Signature Edition (`GROBLE_SIGNATURE_PRODUCT_IDS`, default `8Xy27f`, ₩29,000) issues a **lifetime** key with `edition: 'signature'`, `updatesUntil` (end of the KST day three years after purchase) and `support`. `updatesUntil` is a promise only. The app does not lock when it passes. The two plans are subscriptions on their own cycle and issue a **monthly** or **annual** key with `productId` and `billingCycleMonths`:

- **Hama** (`GROBLE_HAMA_PRODUCTS`, default `SfYBy5:1:3900,vdw3HN:12:39000:8JF8jD`): the user brings their own AI. No hosted AI at all.
- **Rau** (`GROBLE_RAU_PRODUCTS`, default `R3n8zG:1:14900:t3QJ4b,atqjpJ:12:149000:nqSZ94`): [hosted Rau](#hosted-rau) included, with a monthly credit allowance (yearly keys too).

Each entry is `id:months:priceKrw[:optionId]`. Records without `expiresAt` (old one-time, Signature, beta, grandfathered and manual keys) are lifetime. A lifetime key is Signature only when `edition` is `signature`. Event names and fields follow [Groble's event reference](https://groble.im/help/guides/webhook-events).

Stored editions are never rewritten; they read by their current names everywhere (app, website, admin):

| Stored `edition` | Reads as | Why |
| --- | --- | --- |
| `pro`, `basic` | `hama` | The BYOK plan was Pro, then Basic. New Hama keys are still stored as `basic`, because stored `hama` already means the next row |
| `hama`, `rau` | `rau` | `hama` was the old hosted plan, now Rau. New Rau keys are stored as `rau` |
| `signature` | `signature` | |

- `POST /v1/groble/webhook` receives Groble events (register `https://rau-credits-production.up.railway.app/v1/groble/webhook` in Groble 내 스토어 → 연동, events `payment.completed`, `payment.cancel_requested`, `payment.refunded`, `subscription_payment.completed`, `subscription_payment.refunded`, `subscription_payment.failed`, `subscription.cancel_requested`, `subscription.terminated`). It checks `X-Groble-Signature` (or `X-Groble-Signature-Previous`) = HEX(HMAC-SHA256(secret, `${X-Groble-Timestamp}.${rawBody}`)) in constant time against `GROBLE_WEBHOOK_SECRET` and `GROBLE_WEBHOOK_SECRET_PREVIOUS`, rejects timestamps more than 5 minutes off, and dedupes on `X-Groble-Idempotency-Key`.
  - `payment.completed` issues one key per `merchantUid` after checking the product id and that product's own price. Yearly and the paused one-time product expect `GROBLE_EXPECTED_PRICE` (default 9900) and `GROBLE_MIN_AMOUNT`. Signature expects `GROBLE_SIGNATURE_EXPECTED_PRICE` (default 29000) and `GROBLE_SIGNATURE_MIN_AMOUNT`. A Hama or Rau product expects its entry's price (`originalAmount` equal to it, `finalAmount` at least it). Hama and Rau are subscription products, so a `payment.completed` for one is held as `wrong_product`. `GROBLE_PRODUCT_PRICES` (`id:price` or `id:price:min`) overrides one row, e.g. a lower minimum for a coupon. A Signature payment at ₩29,000 is accepted. The same amount on `uRshdR` or `GLJFC9` is held as `wrong_price`. An order that fails a check is **held** (no key) for `orders --status held` and `release`. Releasing a held Signature, Hama or Rau order stamps its edition.
  - `payment.cancel_requested` is recorded only. `payment.refunded` revokes on a full refund (or when partial refunds add up to the paid amount) and records partial refunds. A refund that arrives before its completion means no key is ever issued.
  - `subscription_payment.completed` with `billingReason: INITIAL` issues one key per `merchantUid` (same product and price checks, `paymentType == SUBSCRIPTION`) with `expiresAt` = the end of the KST day `billingCycleMonths` (default 12) after the payment. A product with an option id must be paid as exactly that option: `data.object.options` holds one item with that `optionId` (Groble sends one option, quantity 1, on every subscription event) and its `unitOriginalPrice`, when present, is the list price. Otherwise the order is held as `missing_option`, `wrong_option:<ids>` or `wrong_price:<amount>`. `SfYBy5` has no option on Groble and skips this check. A Hama or Rau product always runs on its configured months: a missing or unreadable `billingCycleMonths` uses them, and an event whose `billingCycleMonths` names another cycle is held as `cycle_mismatch` (initial and renewal rounds), so a monthly buyer never gets a year. Its `sellerReference` links the subscription to the key. `RENEWAL` finds that key by `sellerReference` (else the one live subscription key with the buyer's email) and extends it by the key's own cycle (one month for a monthly key) from its current expiry, or from the day it was paid if it lapsed (a late retry or re-payment starts a new year on its payment day). Each round's `merchantUid` is recorded, so a replay never extends twice. A renewal checks product and currency only, so a later price change never holds old subscribers. An unmatched renewal is held: `extend` the key (a held renewal cannot be `release`d).
  - `subscription_payment.failed` puts the key in `past_due` and keeps it **fully usable past `expiresAt`** through Groble's retry and grace window (3 daily attempts, then 7 days; groble.im/legal/refund 제6조 제13항): until `failure.gracePeriodEndsAt` when the event carries it (the final attempt does), else `expiresAt` + `GROBLE_PAYMENT_GRACE_DAYS` (default 10), and never more than `GROBLE_PAYMENT_GRACE_MAX_DAYS` (default 14) past `expiresAt`, so a monthly key cannot run another month unpaid. `subscription.terminated` or the window's end stops it; a paid retry renews as usual and clears it.
  - `subscription.cancel_requested` and `subscription.terminated` are recorded on the key (`subscription.status` `cancel_requested` / `terminated`, `autoRenew: false`). They never shorten the paid year: an immediate termination (`SELLER_CANCELLED`, `CONTENT_DELETED`) still runs to `expiresAt`. `subscription_payment.refunded` takes back the refunded round's time, and revokes once every paid round of the key is refunded.
  - Unknown event types, events with no `merchantUid` and subscription events with no matching key answer 200 (so Groble stops retrying) and are recorded as held in `webhook-log.json`.
  - Every held order and every such event is emailed to `management@heemangstudios.com` (`held-alert.mjs`, same Resend key and layout as the rejection alert): the reason in Korean, buyer email, amount, `merchantUid` and KST time, never headers, signatures or the body. One email per order or event, with no time window across orders; a replay or re-delivery of the same order and reason is not mailed again (Resend idempotency key `held-<merchantUid>-<reason>`).
  - Replies (Groble retries 408/429/5xx for about 44 hours and treats other 4xx as final; it never gets 3xx or 410):

    | Status | `error` | Why |
    | --- | --- | --- |
    | 200 | | Handled, held or ignored |
    | 503 | `not_configured`, `missing_headers`, `bad_timestamp`, `bad_signature`, `body_too_large` | The signature could not be checked or did not match. Groble keeps retrying while the secret or setup is fixed |
    | 401 | `timestamp_out_of_window` | Signed, but more than 5 minutes off. Replay protection, final |
    | 400 | `json_invalid`, `payload_invalid` | Signed, but the body is unreadable. Final |
    | 500 | `store_error` | Saving failed. Groble retries |
    | 429 | `rate_limited` | More than 30 rejections per IP (300 overall) in 10 minutes. Not recorded |

  - Every rejected webhook and every held order is recorded in `webhook-log.json` (newest 200) with the time, reason, status, whether the signature matched, the request headers without `X-Groble-Signature*`, `Authorization` or `Cookie`, `X-Groble-Timestamp`, `X-Groble-Idempotency-Key`, and the event type, id and `merchantUid` when the body is JSON. For an unverified request those body fields are whatever the sender claimed. Held entries also keep the outcome (`action`), buyer email and amount, and `ackedAt` once the owner dismisses them.
  - Every rejection also emails `management@heemangstudios.com` through Resend after the reply, at most once per reason per 15 minutes; the next email for that reason counts the ones in between. It carries the reason, time and status only. Without `RESEND_API_KEY` the alert is skipped with a log line.
- `GET /v1/groble/webhook` answers 200 when the webhook secret is set and 503 when it is not. The deploy workflow polls it.
- `GET /v1/license/by-ref?ref=` returns `{status:'pending'}`, `{status:'issued', key, licenseExpiresAt}` (epoch ms, `null` for lifetime) or `{status:'revoked'}` for the success page. A Signature key also includes `edition`, `prioritySupport` and `updatesUntil` (epoch ms); a Hama or Rau key includes `edition` (`hama` or `rau`) and `plan`. No buyer data. CORS echoes only `LICENSE_ALLOWED_ORIGINS`. 120 requests per minute per IP.
- `POST /v1/license/activate {key, deviceId, appVersion, platform}`, `POST /v1/license/validate {key, deviceId}`, `POST /v1/license/deactivate {key, deviceId}`. Two devices per paid key; beta keys carry their own limit. Success: `{ok:true, lease, keyId, tier ('paid'|'beta'), expiresAt (lease end, epoch ms), licenseExpiresAt (key end, epoch ms, null = lifetime), autoRenew (null for lifetime), licenseState ('active' | 'payment_failed'), paymentGraceEndsAt (epoch ms while payment_failed, else null), paymentFixUrl (annual keys only: Groble's buyer page where the payment is fixed), devicesUsed, deviceLimit}`. A Signature key adds `edition: 'signature'`, `prioritySupport` and `updatesUntil` (epoch ms) on this JSON only. They are not inside the signed lease, so an old app keeps unlocking a lifetime key and a passed update promise cannot lock the app. Every success also carries `plan` (`monthly`|`annual`|`lifetime`) and `rau: {eligible}` (true for a live Rau key, including its payment grace, and for a live key with an active plan in the frozen `hama.json`; a license never carries the account's trial), and a Hama or Rau key adds `edition`. All of these are additions; older apps ignore them. Errors: `{ok:false, error}` with `invalid_key` (404), `revoked` (403, with `tier`), `expired` (403, an annual key past `expiresAt` and any payment grace, with `tier`, `licenseExpiresAt` and `paymentFixUrl`; deactivate still works), `device_limit` (409), `not_activated` (404, validate on a device that never activated), `device_id_invalid` (400), `server_not_configured` (503).
- A lease is `payload.signature`: `payload = base64url(JSON {v:1, kid, keyId, keyHash, deviceId, issuedAt, expiresAt[, licenseExpiresAt]})`, where `licenseExpiresAt` appears only for annual keys so lifetime leases are unchanged, and `signature = base64url(Ed25519 over the ASCII payload segment)`. Times are epoch ms, valid 7 days (3 days for beta keys). `kid` is `LICENSE_SIGNING_KEY_ID` (default `hama-prod-1`). `keyHash` is hex SHA-256 of the key as the app sent it, trimmed, uppercased and without whitespace, so the app's own normalization of its stored key matches. `license-lease.mjs` `verifyLease(lease, {kid: publicKey}, {deviceId, key})` mirrors the app's check and only needs `node:crypto`. `GET /v1/license/public-key` returns `{alg, kid, rawBase64, spkiDerBase64}`; the app pins `rawBase64` under `kid`.
- `POST /v1/license/grandfather {installId}` returns a free key, once per install, when `sha256(installId)` is in `unique-installs.json` with `os` in `GRANDFATHER_PLATFORMS` (default `darwin`) and `firstSeenAt` before `GRANDFATHER_CUTOFF`. Without the cutoff it answers `grandfather_disabled`.
- Admin (`Authorization: Bearer $ADMIN_TOKEN`): `GET /v1/admin/licenses?key=|keyId=|merchantUid=|email=|ref=`, `GET /v1/admin/orders?status=held|issued|refunded&contentId=`, `GET /v1/admin/webhooks?kind=rejected|held&limit=50`, `GET /v1/admin/licenses/betas`, `GET /v1/admin/licenses/signatures` (Signature buyers: email, key, `updatesUntil`, status), `GET /v1/admin/licenses/customers` (paid keys newest first with `subscriptionStatus` `active`|`past_due`|`lapsed`|`lifetime`, devices and email delivery), `GET /v1/admin/attention` (held orders not yet handled plus held webhook events that hold no order, both until acknowledged), and `POST /v1/admin/licenses/{issue,issue-beta,revoke,restore,reset-devices,remove-device,resend-email,extend}`, `POST /v1/admin/orders/{release,apply-renewal}` and `POST /v1/admin/attention/ack`. `remove-device {keyId|key, deviceId}` frees one device and keeps the others (`device_not_found` 404). `apply-renewal {merchantUid, keyId|key}` applies a held renewal round to the buyer's annual key exactly like a matched webhook (one cycle from its expiry, the round recorded for refunds, the renewal email queued) and links the round's ref to that key. `attention/ack {id}` dismisses a held webhook event and `{merchantUid}` a held order the owner will not release; a newly held round shows again. License views and customers carry `plan` (`monthly`|`annual`|`lifetime`; Hama and Rau views add `billingCycleMonths`), `edition` by its current name, `expiresAt`, `subscription`, `extensions`, `prioritySupport` and, for Signature, `edition`, `productId`, `updatesUntil`, `support` and `supportSlaLabel`. `scripts/license-admin.mjs` wraps them:

  After fixing a `bad_signature` or `not_configured` alert, Groble's retries issue the keys on their own. A final rejection (401/400) never comes back: find its `merchantUid` with `webhooks --rejected`, take the buyer email from Groble and run `issue --merchant-uid ... --email ... --send-email`.

  Beta-tester keys (`beta`, `POST /v1/admin/licenses/issue-beta {name, email?, devices?, note?}`) work like paid keys on macOS and Windows but allow `devices` simultaneous devices (default 5, clamped to 1..50) and get 3-day leases, so a `revoke` locks an online app at its next daily check and an offline one within 3 days. They are never emailed: `beta` prints the key on its last line. `betas` lists each key with its tester, status, devices (platform, last seen) and revocation time. Records without `tier` or `deviceLimit` are paid keys on two devices.

The night-sky header and the wall display show unused, redeemed and last-24-hour redemption counts and the latest redemptions.   A manual key with a `merchantUid` is reused if the Groble webhook for that order arrives later, and a later refund webhook still revokes it. `issue --years N` (or `--until DATE`) makes the manual key an annual key, for a subscription order whose webhook never arrived. `issue --edition signature` makes a Signature key (no `expiresAt`). `--years` together with `--edition signature` is `term_conflict`. `--updates-until YYYY-MM-DD` sets the update promise to the end of that KST day. The default promise is three years from now. `extend` adds N years (default 1) to an annual key from its expiry, or from now if it lapsed; `--until YYYY-MM-DD` sets the end of that KST day. Lifetime keys answer `lifetime_key`. Each extension is kept in the key's `extensions`.
- Key email goes out after the webhook reply through Resend (`RESEND_API_KEY`, `LICENSE_EMAIL_FROM`). Without the API key the attempt is logged and marked `skipped`; the webhook still succeeds and the success page still shows the key. Failed sends retry up to 3 times, including after a restart. Every email is built on `email-layout.mjs` (banner, key card, download button, footer); its images live in `website/assets/email/` on GitHub Pages, and the deploy workflow waits for them to go live before it deploys the server. The key email's copy follows why it went out: a purchase or released hold, a subscription renewal, a Signature purchase, an admin `resend-email`, or an admin `issue --send-email` with no payment behind it. Subscription keys get one line under the key card with the next renewal date (매달 or 매년, or the end date once auto-renewal is off). Hama mail names Hama, the user's own AI (내 AI 연결) and two devices; Rau mail names Rau, the included AI with monthly credits and Rau mode. Plan copy never names a model or AI vendor. A monthly key's renewal sends no key email; Groble sends the receipt. Signature mail names Signature and 우선 지원 · 1영업일, and puts the update-promise date under the card. The card itself holds only the key. A lifetime key that is not Signature gets no date. Support stays email-only at `management@heemangstudios.com`.

### Gift credits (SPECIAL EVENT)

A one-time gift of Claude usage for Pi (`GIFT_AMOUNT_USD` unless the key has its own amount), one per beta license key (`tier: 'beta'`, shared by its devices) on macOS and Windows. Paid and grandfathered keys do not get it. The app authenticates with its license lease as `Authorization: Bearer <lease>`; the server checks its own signature, expiry, that the license is active, that the lease's device is still activated, and the key hash. Anything else is `unauthorized` (401). A valid lease is `not_eligible` unless the key is a beta key and the device's `platform` is in `GIFT_PLATFORMS`; this is checked on every status, claim and proxy call.

- `GET /v1/gift/status` → `{ok, event:{id, amountUsd, endsAt, active}, eligible, claimed, remainingUsd, usedUsd, claimedAt}`. `event.amountUsd` is this license's amount: its key's limit once claimed, else its allocation, else `GIFT_AMOUNT_USD`. An unclaimed key allocated $0 is `eligible: false`. Balances come from the key's `limit_remaining` on OpenRouter (BYOK spend plus OpenRouter fees), cached 15 s, and are `null` when it does not answer.
- `POST /v1/gift/claim` (body `{}`) is idempotent. The first call creates one OpenRouter key named `hama-gift-<event>-<keyId>` with `limit` = the license's amount and `include_byok_in_limit: true`, and keeps the key in `gifts.json`; it is never sent to the app. Errors: `unauthorized` 401, `not_eligible` 403 (also for a $0 allocation), `event_inactive` 410 (event not configured or past `GIFT_ENDS_AT`), `budget_exhausted` 409 (the created limits would pass `GIFT_TOTAL_BUDGET_USD`), `upstream_unavailable` 502. A claim interrupted after OpenRouter created the key leaves a `provisioning` record; the next claim deletes keys with that name before creating a new one.
- OpenAI-compatible proxy at `/v1/gift/openrouter` (Pi `baseUrl`, lease in place of the API key). Errors use OpenRouter's `{error:{code,message}}` shape: 401 `unauthorized`, 403 `not_eligible` or `gift_not_claimed`, 410 `event_inactive`, 402 `Insufficient credits: ...` once the key limit is spent or the gift is disabled.
  - `POST /chat/completions` streams SSE through as it arrives, and a client disconnect aborts the upstream request. Models must start with one of `GIFT_MODEL_PREFIXES` (also every entry of `models`); `max_tokens`/`max_completion_tokens` are clamped to `GIFT_MAX_OUTPUT_TOKENS` and `max_tokens` is set when neither is given. Bodies up to 16 MiB, 4 concurrent requests and 60 per minute per license.
  - `GET /models` is the OpenRouter catalog filtered to the allowed prefixes, cached 10 minutes. `GET /auth/key` (and `/key`) and `GET /credits` answer OpenRouter-shaped balances for the gift.
- Admin: `GET /v1/admin/gifts?status=&eventId=` lists grants without their keys plus `committedUsd` and `allocations`; `POST /v1/admin/gifts/disable {keyId, reason}` disables the OpenRouter key (`PATCH /keys/{hash} {disabled:true}`) and marks the grant `revoked`. A revoked license loses the gift at once because its lease no longer authenticates.
- Per-key amounts: `POST /v1/admin/gifts/amount {keyId, amountUsd}` (beta keys only, 0–1000, rounded to cents) stores `allocations[keyId]` for the current event. On a claimed key it first sets the OpenRouter limit (`PATCH /keys/{hash} {limit}`) and then `limitUsd`; lowering below what was spent leaves the gift used up, and $0 is refused by the proxy itself. A raise must fit `GIFT_TOTAL_BUDGET_USD` (`budget_exhausted` 409); while a change is on its way, or after a PATCH that failed without a clear answer, it stays counted as `pendingLimitUsd`. A revoked gift only stores the amount. Errors: `amount_invalid` 400, `invalid_key` 404, `gift_provisioning` 409 (claim in progress), `upstream_unavailable` 502. `POST /v1/admin/licenses/issue-beta` also takes `giftUsd`, and `GET /v1/admin/licenses/betas` adds `giftEvent` and each key's `gift: {amountUsd, status: unclaimed|provisioning|active|revoked, limitUsd, usedUsd, remainingUsd, claimedAt}` (`null` without an event; balances from the 15 s cache, `null` when OpenRouter does not answer).

### Hosted Rau

Rau keys, keys with an active plan in the frozen `hama.json`, and accounts in their [trial](#accounts) get hosted Rau: the Rau agent (Pi's harness runs through this server) and Rau-0.1, the taste learner in `rhwp/rhwp-agent/taste-learner.mjs`. The app never holds a provider key. It authenticates with its lease as `Authorization: Bearer <lease>` or `x-api-key: <lease>` (the same check as gifts; a v1 license lease or a v2 account lease). A lease that is not ours, expired, or for a removed device is `unauthorized`; a valid lease without Rau hears `rau_plan_required` with `upgradeUrl` (`RAU_UPGRADE_URL`).

Hosted Rau runs while `RAU_ENABLED` is not `false` and the models in `RAU_MODEL` have at least one upstream key; otherwise status and learn answer 503 `rau_not_configured` and the agent 503 `not_configured`.

- **Models and routes** (`rau-proxy.mjs`). `RAU_MODEL` is an ordered list of `haiku` and `deepseek` (default `haiku`); the first serves every call and the rest are fallbacks. `haiku` is OpenRouter `anthropic/claude-haiku-4.5` on its Anthropic-compatible `POST {OPENROUTER_API_BASE}/messages` with `RAU_OPENROUTER_KEY`, then Anthropic `claude-haiku-4-5` (`{ANTHROPIC_API_BASE}/v1/messages`, `ANTHROPIC_API_KEY`) as the backup. `deepseek` is OpenRouter `deepseek/deepseek-v4.1-flash` on the same `/messages`, pinned to one provider with `provider: {only: [RAU_DEEPSEEK_PROVIDER], allow_fallbacks: false}` (default `deepinfra`) so its price stays known. `RAU_MODEL=deepseek` switches by hand; `haiku,deepseek` keeps DeepSeek as the last fallback. A route without its key is left out. Model ids are code constants: no variable adds another model.
- **Failover** only before any byte reached the client: on a network error or timeout, 408, 429, 5xx (529 included), 401/402/403, a 400 about credit or billing, or a 200 stream whose first event is an overloaded, api or rate-limit error. A session served by a backup route is pinned to it for 30 minutes, refreshed on every call it serves (prompt caches are per provider); a pinned session tries its pinned route first, then the others in order, and the primary serving it again unpins it. Sessions are Pi's `x-session-id` when sent, else a hash of the principal, system prompt and first user message. When the last route fails on our credentials or billing the answer is 502 `upstream_unavailable`; its overload or rate limit keeps its status so Pi retries; any other 4xx is the client's own and keeps its status. The body is always ours (`{type:'error', error:{type, message}}` with the Anthropic error type for the status and a message that names no model or vendor; a context overflow keeps `prompt is too long` and its token counts so Pi compacts); the upstream's own error goes to the log with keys masked.
- **Credits.** Each principal has one ledger in `rau.json` (`rau-ledger.mjs`): a Rau license (ledger id = keyId) spends `RAU_MONTHLY_ALLOWANCE_USD` (default 8) per month, yearly keys included; months start on the anchor's day and time (UTC), clamped to short months, and the anchor is the subscription's first payment, else the key's creation, else the legacy plan's `periodAnchor`. A trial (ledger id = accountId) spends $2 over its 7 days. A call is refused **before** upstream once the period's spend reaches the allowance, so the last admitted call may overshoot by its own cost (and calls in flight together by theirs). Each call bills once by its message or generation id (the last 500 ids of the last 24 hours are kept).
- **Billing** is the real price of the model that served: Haiku 4.5 at $1 input, $5 output, $0.10 cache read, $1.25 cache write (5 m) and $2 (1 h) per million tokens on both routes, never OpenRouter's reported cost; DeepSeek at OpenRouter's reported `usage.cost`, else $0.14 / $0.42 / $0.0042 (cache writes as input), a conservative row for DeepInfra. Usage is read from the stream as it passes, without holding bytes back. A stream cut before its final usage (client disconnect, upstream drop) is billed by estimate: reported input plus at least 1 output token per 3 bytes of streamed text, or 1 input token per 3 request bytes when nothing was reported. A client that leaves after the request went upstream, before any answer or while the first event is checked for failover, is billed the same estimate. Every call also adds to a weekly spend by model (UTC weeks from Monday, 26 kept).
- `GET /v1/rau/status` → `{ok, eligible, source: 'plan'|'trial'|null, reason: null|'rau_plan_required', upgradeUrl, allowanceUsd, usedUsd, remainingUsd, resetsAt (ISO; the next monthly reset, or the trial's end), agent: {baseUrl: '/v1/rau/agent', model: 'rau', contextWindow: 200000, maxOutputTokens: 16000}}`; the usage fields are `null` when not eligible. 120 per IP per minute. A trial whose $2 is spent stays eligible with `remainingUsd: 0` until its end, so the agent answers 429 `rau_credits_exhausted` and Rau-0.1 402 (reset = the trial's end); after its 7 days it is not eligible (403 `rau_plan_required`).
- `POST /v1/rau/agent/v1/messages` (Pi `anthropic-messages`, `baseUrl = <site>/v1/rau/agent`): Anthropic Messages with `model: 'rau'`, streamed through as it arrives; a client disconnect aborts the upstream call. The body is trimmed for Haiku 4.5: only Messages fields pass (`models`, `provider` and other routing or tier fields are dropped), `max_tokens` is clamped to 16000 (set when missing), `output_config.effort` is removed, a thinking budget is kept below `max_tokens` and dropped when it cannot reach 1024, and adaptive thinking is dropped. Server tools and `mcp_servers` are refused because they bill outside token usage. Client auth headers are dropped; only `anthropic-version` (default `2023-06-01`) and `anthropic-beta` are forwarded. Errors use `{type:'error', error:{type, message}}`: 401 `unauthorized`, 403 `rau_plan_required`, 429 `rau_credits_exhausted` (message holds `quota exceeded` and `[rau-credits:<ISO resetsAt>]`, with `Retry-After` and `X-Rau-Resets-At`), 429 `rate_limited` (4 concurrent and 60 per minute per principal), 400 `model_not_allowed`/`tool_not_allowed`/`invalid_request`, 413 `too_large` (16 MiB), 502 `upstream_unavailable`, 503 `not_configured`.
- `POST /v1/rau/learn {prompt}` (Rau-0.1): `prompt` is a non-empty string of at most 48 KB UTF-8, sent through the same chain as one user message, not streamed, `max_tokens` 2000, no thinking. Answers `200 {ok:true, text, model:'rau-0.1', usage:{allowanceUsd, usedUsd, remainingUsd, resetsAt}}`, `text` being the reply's text blocks joined. Errors are `{ok:false, error, ...}`: 400 `invalid` with `field` (`prompt` or `body`), 401 `unauthorized`, 403 `rau_plan_required` with `upgradeUrl`, 402 `rau_credits_exhausted` with `allowanceUsd`, `usedUsd` and `resetsAt`, 429 `rate_limited` with `Retry-After` (2 concurrent and 20 per minute per principal, 120 per minute per IP), 502 `upstream_unavailable`, 503 `rau_not_configured`.
- Admin (`ADMIN_TOKEN`): `GET /v1/admin/rau` lists ledgers (principal id, source, allowance, this period's spend, remaining, calls and end, totals; no keys or emails) with the configured routes; `GET /v1/admin/rau/spend?weeks=8` (1–26) answers the spend per week and model (`usd`, `calls`, input, output and cache tokens, `routes` in USD) and the totals.

```sh
node scripts/license-admin.mjs rau                   # one line per ledger
node scripts/license-admin.mjs rau-spend --weeks 8   # spend per week and model, with totals
```

What the earlier plans left behind:

- `hama.json` is **frozen**. It is read once, on first use, for plans that were active (admin-enrolled keys and old hosted Hama keys) and never written again (`hama-legacy.mjs`; in Postgres mode `hama_plans`, imported from the file); such a key keeps Rau while its license is live. Its ledgers and usage logs (`hama-usage/`) are not read, and the usage logs are not imported.
- `rau.json` may still hold an `allowances` field: the per-license OpenRouter keys of the earlier Rau-0.1, named `hama-rau-<keyId>`. It is never read or changed. The owner may delete those keys on OpenRouter (Settings → API keys).
- The old hosted Hama routes (`/v1/hama/*`, `/v1/admin/hama*`) and the `X-Hama-Plan-Names` header are gone; plan names are the new ones for every client.

Owner setup: set `RAU_OPENROUTER_KEY` (an OpenRouter key with a hard credit limit; `HAMA_OPENROUTER_KEY` is read while it is unset) and `ANTHROPIC_API_KEY` for the backup, and choose `RAU_MODEL` and `RAU_MONTHLY_ALLOWANCE_USD`. OpenRouter BYOK is per account: if that account routes Anthropic through the gift setup's BYOK key with shared capacity off, the Anthropic backup reaches the same key and fails with it, so keep the Rau key in an account (or workspace) without that rule. DeepSeek through OpenRouter's `/messages` (with `provider.only` and its reported cost) is unverified until one real call: try `RAU_MODEL=deepseek` once and compare `rau-spend` with OpenRouter's activity page before relying on it.

Keys look like `HAMA-XXXXX-XXXXX-XXXXX-XXXXX-XXXXX` (125 random bits, Crockford base32). Every write goes through its store's exclusive update (an atomic temp-file rename, or one Postgres transaction under the domain's advisory lock). Rate limits, in-flight counts and Rau session pins live in memory, so the server assumes **one replica**.

### Accounts

HamaEditor accounts sign in with WorkOS AuthKit (email magic link on the AuthKit page, or Google) through the system browser and a loopback callback in the app. `accounts.mjs` owns accounts, devices and sessions; `workos.mjs` is the only outbound call (10 s timeouts). The plan follows the account's linked licenses, and the app gets an account lease (v2) instead of a license lease. Every `/v1/account/*` route answers `503 accounts_not_configured` until `WORKOS_API_KEY` (and the license signing key, which signs the account lease) is set. They are app routes: no CORS. Errors are `{ok:false, error, ...extra}`.

- `GET /v1/account/auth/providers` → `{ok, providers}` from `ACCOUNT_AUTH_PROVIDERS`. `email` is AuthKit's own page (`provider=authkit`, with `login_hint` when given), `google` `GoogleOAuth`. Any other id fails startup.
- `POST /v1/account/auth/start {provider, challenge, port, state, loginHint?}` → `{ok, url, expiresAt}`: `challenge` is base64url(SHA-256(PKCE verifier)), `port` the app's loopback port (1024–65535), `state` the app's nonce (`[A-Za-z0-9_-]{16,128}`). The login lives 10 minutes; `url` is the WorkOS authorize URL with the login id as `state`. Errors: 400 `invalid` with `field`, 400 `provider_unavailable`, 429 `rate_limited` (20 per IP per 10 minutes).
- `GET /v1/account/auth/callback` is the WorkOS redirect target. It takes the login (single use), exchanges the code with `WORKOS_API_KEY`, finds the account by WorkOS user, else by verified email, else creates one, and answers 302 to `http://127.0.0.1:<port>/auth/callback?code=<grant>&state=<app state>`. A WorkOS error answers the same URL with `error=auth_cancelled` (`access_denied`) or `auth_failed`. An unknown or expired login gets a one-line Korean page and no redirect. Codes, grants, sessions and full emails are never logged. A verified email then links that email's licenses to the account.
- `POST /v1/account/auth/token {code, verifier, device:{id, name, platform, appVersion}, replaceDeviceId?}` → `{ok, session, ...account}`. The grant is single use, bound to the PKCE challenge, valid 10 minutes and 10 attempts; every failure is 400 `grant_invalid`. An account holds `ACCOUNT_DEVICE_LIMIT` devices; the same device id signing in again replaces its session and keeps its slot. At the limit it answers 409 `device_limit {limit, devices}` (the grant stays), and a retry with `replaceDeviceId` removes that device and its session first (404 `device_not_found` for another id). 30 per IP per 10 minutes.
- Session routes take `Authorization: Bearer hes_...`. A session is per device, stored only as its SHA-256, and is invalid (401 `session_invalid`) once its device is removed, it signed out, the account is gone, or it was not used for 180 days. `POST /v1/account/refresh {appVersion?}` → the account payload with a fresh lease; it marks the device seen (at most once an hour) and links licenses of a verified email bought since. `POST /v1/account/signout` removes this device and is idempotent. `POST /v1/account/devices/remove {deviceId}` → `{ok, signedOut:false, devices}`, or `{ok, signedOut:true}` for the calling device; 404 `device_not_found`.
- `POST /v1/account/redeem {key}` links a key the user typed (any spacing or case; the `HAMA-` prefix is optional) → `{ok, alreadyLinked, license, ...account}`, where `license` is the key as `licenses` lists it. Errors: 400 `invalid_format`, 404 `invalid_key`, 403 `revoked`, 409 `key_linked_elsewhere`. 20 per account per hour (429 `rate_limited`, failures count).
- `POST /v1/account/claim {orderId, email}` links the key of a Groble order bought with another email: `orderId` is the Groble order number (`merchantUid`) and `email` the buyer email on that order (any case). Same answer as redeem. An unknown order, a wrong email or an order without a key is 404 `order_not_found` (one code, so neither can be probed); a held order is 409 `order_not_ready`; also 403 `revoked` and 409 `key_linked_elsewhere`. 10 per account per hour.
- `POST /v1/account/profile {name}` → `{ok, account}`. 1–30 characters, no control characters (400 `name_invalid`). A name the user set is never replaced by a later sign-in.
- `PUT /v1/account/avatar` with the picture as the raw body (`Content-Type` `image/jpeg`, `image/png` or `image/webp`, at most 1 MiB) → `{ok, avatar:{rev, type, bytes}}`. The first bytes must match the type. Errors: 413 `too_large` (a body declared past 2 MiB is refused unread), 415 `unsupported_type`, 429 `rate_limited` (30 per account per hour). It is stored as `avatars/<accountId>.<ext>` (temp file and rename, mode 0600), or in `account_avatars` with `DATABASE_URL`, and `rev` goes up by one on every upload, also after a removal. `GET /v1/account/avatar` → the bytes with `Content-Type`, `ETag: "<rev>"` (304 for a matching `If-None-Match`) and `Cache-Control: private, no-cache`; 404 `no_avatar`. `POST /v1/account/avatar/remove` → `{ok}`.
- `POST /v1/account/stats {batchId, agentSessions, documentsEdited}` → `{ok, stats}` adds the app's activity counts (integers 0–1000; `batchId` `[A-Za-z0-9_-]{8,64}`). A batch id among the account's last 50 is a no-op, so a retried flush counts once. 400 `invalid` with `field`.
- `POST /v1/account/delete {confirm}` → `{ok}`. `confirm` is the account email (any case; 400 `confirm_mismatch`). While a linked key is live and auto-renewing (`subscription.autoRenew` not false and not terminated) it answers 409 `subscription_active {manageUrl}` (`GROBLE_PAYMENT_FIX_URL`) and changes nothing; a cancel request, a terminated subscription, a lifetime key or a gift key does not block. Then, without holding both locks: the keys are unlinked (`unlinkedBy: 'delete'`, so the same email links them to a new account), the account with its devices, sessions, picture, stats and trial is removed, and the WorkOS user is deleted best effort (a failure is logged and the answer is still 200). Rau ledgers stay on their license keys, and the email's trial record stays, so the email gets no second trial.
- `POST /v1/account/rau-trial` (body `{}`) starts the account's Rau trial: 7 days and $2 of [hosted Rau](#hosted-rau), once per account and once per email (`trialEmails` keeps sha256 of the lowercased email past the account's deletion). Answers the account payload with the trial active. Errors: 409 `trial_used`, 409 `rau_active` (a live Rau key), 503 `rau_unavailable` (hosted Rau not configured), 429 `rate_limited` (10 per account per hour, failures count), 401 `session_invalid`.
- The account payload: `account {id, email, name, avatar, provider, createdAt}`, `plan {tier, keyId, edition, plan, expiresAt, autoRenew, paymentFailed, paymentGraceEndsAt, manageUrl, rau}`, `trial {state, startedAt, endsAt, days: 7, allowanceUsd: 2}`, `licenses` (masked keys, primary first), `devices` (newest first, `current` marks the caller), `deviceLimit`, `stats {agentSessions, documentsEdited, since}`, `lease` and `leaseExpiresAt`. `plan.rau` is `{eligible, source: 'plan'|'trial'|null, allowanceUsd, usedUsd, remainingUsd, resetsAt}` (`resetsAt` the next monthly reset, or the trial's end; all `null` when not eligible). `trial.state` is `available` (never used by this account or its email), `active` (inside its 7 days with credits left) or `ended`. Times are epoch ms except `account.createdAt` (ISO).
- Tier: a linked license is live while active and before its expiry plus payment grace (lifetime keys always). Rank 2 is a live key with Rau (`tier: 'rau'`), 1 every other live key (`hama`: Hama, beta, Signature, GLJFC9, lifetime, grandfathered and manual keys); no live license is `free`. An active trial makes the tier `rau` while no Rau key is live, and the primary license stays what it was. The primary license is the highest rank, then a Hama or Rau subscription, then the latest end, then the oldest.
- Licenses link on the license record (`accountId`, `linkedAt`, `linkedBy`): every non-revoked key bought with the account's **verified** email (`email`), a Groble purchase whose buyer email belongs to a verified account at once (`purchase`), a redeemed key (`redeem`), a claimed order (`claim`), a redeemed gift code (`gift_code`) and an admin link (`admin`). An unverified email links nothing, and a key an admin unlinked is never linked back by email.
- Account lease: `payload.signature` like the license lease, same key and `kid`, payload `{v:2, kid, accountId, deviceId, keyId (primary or null), tier, plan, issuedAt, expiresAt[, licenseExpiresAt][, paymentGraceEndsAt]}`, valid 7 days (3 when the primary key is a beta key). `license-lease.mjs` `signAccountLease` and `verifyAccountLease(lease, keys, {deviceId, accountId})` (reasons as `verifyLease`, with `wrong_account`); each version's verifier rejects the other. Gifts and hosted Rau accept both: a v1 lease authenticates as before (and never carries the trial), and a v2 lease needs its account and a live session on its device, then picks what serves it now: a live beta key for the gift; for Rau the best live Rau key, else the account's trial while it runs. Rau answers `rau_plan_required` to an account without either; the gift answers 401.
- Admin: `GET /v1/admin/accounts?email=|id=|keyId=` → `{ok, accounts}` with devices, stats and linked licenses (never sessions or grants). `POST /v1/admin/accounts/unlink {keyId}` → `{ok, changed, license}` frees a key from its account; `POST /v1/admin/accounts/link {keyId, accountId}` → `{ok, previousAccountId, license}` links it to an existing account (`account_not_found` 404), moving it from any other. License views carry `accountId`, `linkedBy`, `linkedAt` and `unlinkedAt`.

```sh
node scripts/license-admin.mjs accounts --email user@example.com   # or --id acct_... | --key-id lic_...; last lines: <id> <email> · 기기 N · 키 <keyId> <status>
node scripts/license-admin.mjs account-unlink --key-id lic_...
node scripts/license-admin.mjs account-link --key-id lic_... --account-id acct_...
```

### Gift codes

An admin issues a batch of codes; a signed-in user redeems one for a Hama or Rau key of a fixed term, linked to their account. The issue and redeem logic is in `licenses.mjs` (redeeming a code and creating its key is one mutation of the licenses store), the code format and plan names in `gift-codes.mjs`.

- Codes are `GIFT-XXXX-XXXX-XXXX-XXXX`: 16 Crockford base32 characters, 80 random bits. Input is normalized like a license key (case, spaces, dashes, a missing `GIFT-` prefix, O → 0, I/L → 1). The server stores only the SHA-256 of the normalized code and its first group (`GIFT-XXXX`); the plaintext is in the issue answer and nowhere else, never in logs, lists or `licenses.json`.
- `POST /v1/admin/gift-codes/issue {plan, durationMonths | durationDays, count, note?, redeemBy?}` (`ADMIN_TOKEN`) → `{ok, batch, codes}`. `plan` is `hama` or `rau` (`basic` and `pro` are still read as `hama`; `hama` never means Rau) and the term exactly one of `durationMonths` (1–120) or `durationDays` (1–3660); neither has a default. `count` is 1–1000. `redeemBy` (`YYYY-MM-DD` = end of that KST day, or ISO-8601, in the future) is the last moment a code can be redeemed. Errors (400): `plan_required`, `plan_invalid`, `duration_required`, `duration_conflict`, `duration_invalid`, `count_invalid`, `redeem_by_invalid`; 403 `forbidden`.
- `GET /v1/admin/gift-codes?batchId=&status=` → `{ok, count, batches}`, newest first. Each batch has its fields with `plan` by its current name (`hama` or `rau`), `counts {active, redeemed, revoked, expired}` and `codes` (filtered by `status`): `{codeHash, maskedCode, status, createdAt, redeemedAt, accountId, keyId, revokedAt}`. `codeHash` is the stored SHA-256, an opaque id that cannot give the code back. `expired` is an unredeemed code past its batch's `redeemBy`. 400 `status_invalid`.
- `POST /v1/admin/gift-codes/revoke {batchId | code | codeHash, reason?}` → `{ok, changed, batch}` revokes unredeemed codes: every one of a batch, or one code by its plaintext or its listed `codeHash`. A redeemed code is 409 `code_redeemed {keyId}`; revoke its key with `/v1/admin/licenses/revoke` instead. Errors: 400 `target_required` (not exactly one target), 400 `invalid_format`, 404 `invalid_code`, 404 `batch_not_found`.
- `POST /v1/account/gift-codes/redeem {code}` (account session) → `{ok, alreadyRedeemed, license, ...account}`, like `/v1/account/redeem`. The new key is `{source: 'gift_code', edition, expiresAt, giftBatchId}` with the batch's stored edition (`basic` for Hama, `rau` for Rau), linked with `linkedBy: 'gift_code'`. Its term starts at redemption: `durationMonths` ends like a subscription round (end of the KST day that many calendar months later), `durationDays` at the end of the KST day that many days later. The same account again gets `alreadyRedeemed: true` and the same key. Errors: 400 `invalid_format`, 404 `invalid_code`, 409 `code_redeemed` (another account), 410 `code_revoked`, 410 `code_expired` (past `redeemBy`), 401 `session_invalid`, 429 `rate_limited` (10 per account per hour, failures count), 503 `accounts_not_configured`.
- A gift key is a Hama or Rau key for every entitlement: account tier, primary license and, for Rau, [hosted Rau](#hosted-rau) with the monthly allowance, its months anchored at redemption (the key's creation). It never renews: `plan: null` and `autoRenew: false` in the account payload, its `licenses` entry and the license lease, `manageUrl: null`, no `paymentFixUrl`, no key email, and it never blocks account deletion. At `expiresAt` it lapses like any key; an admin can `extend` or `revoke` it like any key.

```sh
node scripts/license-admin.mjs gift-codes issue --plan hama|rau --months N | --days N --count N [--note "..."] [--redeem-by YYYY-MM-DD] [--out codes.csv]
node scripts/license-admin.mjs gift-codes list [--batch-id gcb_...] [--status active|redeemed|revoked|expired]
node scripts/license-admin.mjs gift-codes revoke --batch-id gcb_... | --code GIFT-... [--reason "..."]
```

`issue` prints the codes once, one per line after the JSON. With `--out` they go only to that file (CSV `code,batch_id,plan,duration_months,duration_days,redeem_by`, mode 0600, created before the request and never overwritten), and stdout shows the batch without them. Nothing else ever prints a code.

Storage (two flat maps in `licenses.json`, `gift_code_batches` and `gift_codes` in Postgres):

- `giftCodeBatches: { [batchId]: { batchId, plan, durationMonths | durationDays, count, note?, redeemBy?, createdAt } }`, `batchId` = `gcb_` + 18 hex. `plan` is the edition the batch's keys are stored with: `basic` (Hama) or `rau`; batches issued before the 2026-10-31 rename hold `basic` or `hama` (the old hosted plan, read as Rau).
- `giftCodes: { [codeHash]: { codeHash, batchId, prefix, status: 'active'|'redeemed'|'revoked', createdAt, redeemedAt?, accountId?, keyId?, revokedAt?, revokeReason? } }`. `expired` is derived from the batch's `redeemBy`, never stored.

Open owner calls, deliberately not decided in code: which plan and term each batch grants (both required, no defaults); whether existing keys stay lifetime and any cutoff for key-only (v1) activation, which gift codes do not change; and whether a code whose account was deleted may be redeemed again by a new account (today it answers 409 `code_redeemed`; `account-link` moves the freed key by hand).

With `DATABASE_URL` set, these files move to Postgres and the server never reads or writes them (the schema is in `migrations/001_licenses_accounts.sql`, `002_stores.sql` and `003_rau_credits_trials.sql`):

| File | Tables |
| --- | --- |
| `licenses.json` | `licenses`, `license_subscriptions`, `license_devices`, `groble_orders` (one row per `merchantUid`), `groble_refs`, `groble_webhook_deliveries` (by idempotency key), `grandfathered_installs`, `gift_code_batches`, `gift_codes`. `keyIndex` is derived from `licenses.key` |
| `webhook-log.json` | `webhook_log` |
| `accounts.json` | `accounts` (`rauTrial` as json), `account_devices`, `account_sessions`, `account_logins`, `account_grants`, `account_email_index` (`byEmail`), `account_workos_index` (`byWorkosUser`), `account_trial_emails` (`trialEmails`), `account_roots` (whether the file holds `trialEmails`: one written before the trial has none) |
| `avatars/` | `account_avatars` (bytes, one row per account) |
| `hama.json` | `hama_plans`, `hama_ledgers` (buckets, call ids and the period as json). Imported once, then only read. `hama-usage/` is not imported, and `hama_usage` (002) stays empty |
| `rau.json` | `rau_ledgers` (the period and call ids as json), `rau_spend` (one row per week and model), `rau_allowances` (the earlier Rau-0.1's keys, the monthly ledger as json), `rau_roots` (which of `allowances`, `ledgers` and `spend` the file holds) |
| `gifts.json` | `gift_credit_events`, `gift_credit_grants`, `gift_credit_allocations` |
| `waitlist.json` | `waitlist_entries` (by lowercased email) |
| `unique-installs.json` | `unique_installs` (by install digest) |
| `downloads.json` | `download_counts`, one row per KST day and `platform\|version` |
| `feedback/index.json` | `feedback_reports`. Each report's `feedback/<id>/` directory stays on the volume, and pruning removes the row first, then the directory |

Only `feedback/<id>/` stays on the volume in Postgres mode, and the 8 MiB limit of a JSON file does not apply to tables. Each service writes only its own tables, in one transaction per change under a per-domain advisory lock, with `site_store_versions` telling processes when to reload. Foreign keys stay inside one domain. A record's fields that have no column, or whose value does not fit theirs exactly (a time that is not a canonical ISO string, an explicit `null`), are kept verbatim in its `extra` json column, so a table row reads back as exactly the JSON it came from. `schema_migrations` records the applied migrations, and `site_meta` holds markers such as a finished import.

## Run and deploy

```sh
npm ci
npm test
npm start          # http://127.0.0.1:5180
```

`npm test` (`scripts/test.mjs`) runs every `tests/*.test.mjs`. The Postgres tests use `SITE_API_TEST_DATABASE_URL`, one throwaway schema per test file. Without it the script starts a temporary cluster with `initdb` and `pg_ctl` from `PATH`, Homebrew's `postgresql@*` or `/usr/lib/postgresql/*` on a free port, and removes it afterwards. With no Postgres binaries those tests skip; `SITE_API_REQUIRE_POSTGRES=1` (set in CI, with a `postgres:17` service) makes them fail instead.

Production stays on the JSON files until `DATABASE_URL` is set on `rau-credits`. Do not set it before the files are imported into Postgres: the server would refuse to start. With `DATABASE_URL` the server finishes its requests and closes the pool on SIGTERM, and `GET /healthz` answers `{ok: true, storage: 'postgres'}` (`'files'` without it).

Production is the Railway project `rau-credits`, service `rau-credits` (`https://rau-credits-production.up.railway.app`), with a volume mounted at `/data`. Deploys go through the GitHub Actions workflow below. Keep the service's GitHub source disconnected (Railway → rau-credits → Settings → Source) so a merge deploys once. For a manual deploy, link this directory once with `railway link` and run `railway up` from `site-api/`. `railway.toml` sets the start command and the `/healthz` health check.

Before a Signature test buy, set these Railway variables on `rau-credits` (the code defaults match, and the Groble product `8Xy27f` stays a draft until Finance starts the sale):

```
GROBLE_SIGNATURE_PRODUCT_IDS=8Xy27f
GROBLE_SIGNATURE_EXPECTED_PRICE=29000
GROBLE_SIGNATURE_MIN_AMOUNT=29000
```

Leave `GROBLE_SUBSCRIPTION_PRODUCT_IDS=GLJFC9` and `GROBLE_EXPECTED_PRICE=9900`. Leave `GROBLE_ONETIME_PRODUCT_IDS=uRshdR` so old refunds still resolve. Do not start the Groble sale from this repo.

On main, `.github/workflows/site-api-deploy.yml` does this automatically for any change under `site-api/`: it runs the tests (with a throwaway `postgres:17` service for the Postgres tests), runs `railway up site-api --path-as-root --service rau-credits --environment production --ci` with the `RAILWAY_TOKEN` repository secret (a Railway **project** token for the production environment), then waits up to 10 minutes for `GET /v1/groble/webhook` to answer 200 (404 = the old deployment is still live, 503 = webhook secret missing) and checks that `/v1/license/public-key` answers 200 (503 = signing key missing). Roll back with Railway → service → Deployments → previous deployment → Redeploy; `licenses.json` on the volume is untouched by a rollback. Once `DATABASE_URL` is set, roll back only to a build that reads it: an older one would serve the stale JSON files. A build that finds a migration newer than its own logs it and starts.

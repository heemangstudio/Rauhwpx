# site-api

Small Node service behind the website beta form, the desktop install counter, accounts, licenses and issue reports. It has no dependencies and stores everything as files in one data directory.

## Routes

- `POST /v1/waitlist` takes `{ email }` from the website's 체험 신청 form. The body is sent as `text/plain` so the cross-origin call needs no preflight. CORS is open, and each IP may submit 10 times per 10 minutes. Each email is stored once.
- `GET /v1/waitlist` lists signups for `Authorization: Bearer $RAU_WAITLIST_ADMIN_TOKEN`. Without that variable the list stays closed.
- `POST /v1/unique-installs` records the first launch of a desktop install. `desktop/unique-install.mjs` signs the ping with the shared key in `unique-installs.mjs`.
- `GET /v1/unique-installs` returns the public total, and `GET /unique-installs` renders it as a page.
- `POST /v1/downloads {platform, version}` counts a download start from the website (`navigator.sendBeacon`, `text/plain`, CORS open). `platform` is one of `mac-arm64`, `mac-x64`, `win-x64`, `win-arm64`, `linux-x64`; `version` is `latest` or `x.y.z[-tag]`. 30 per IP per 10 minutes in memory. `downloads.json` keeps counts only, by KST day and `platform|version` (64 pairs a day, 400 days); no IP, user agent or identifier is stored. `GET /v1/admin/downloads?days=30` (`ADMIN_TOKEN`) and `license-admin.mjs downloads [--days N]` read them.
- `POST /v1/feedback` takes a desktop 문제 보고 (wire contract v1 in `feedback.mjs`): message, optional reply email, meta, diagnostic log, screenshot, chat and document, at most 40 MiB of JSON. `proof` is hex HMAC-SHA256 with the shared key in `feedback.mjs` over `${installId}\n${createdAt}\n${sha256hex(message)}`, and `createdAt` must be within 24 hours of server time. Answers `201 {ok, id}`, or `{ok:false, error}` with 400 `invalid` (plus `field`), 401 `bad_proof`, 413 `too_large`, 429 `rate_limited` (5 per install, 20 per IP per hour, checked before the body is read), 503 `busy` (3 uploads already in flight) and 507 `storage_full`. Each report pings the waitlist Telegram chat.
- `GET /v1/admin/feedback` lists reports newest first with status counts and storage use; `GET /v1/admin/feedback/report?id=` returns one; `GET /v1/admin/feedback/attachment?id=&name=screenshot|log|chat|document` returns a stored file; `POST /v1/admin/feedback/status {id, status: new|seen|resolved}` and `POST /v1/admin/feedback/delete {id}` change it. All need `ADMIN_TOKEN`.
- `GET /healthz`, `GET /rau.png` and `GET /favicon.ico`.

### License keys (HamaEditor on Groble)

Five kinds of Groble products can issue keys. The paused one-time product (`GROBLE_ONETIME_PRODUCT_IDS`, default `uRshdR`) still issues a **lifetime** key with no edition, so a refund of an old order keeps working. The 12-month auto-renewing subscription (`GROBLE_SUBSCRIPTION_PRODUCT_IDS`, default `GLJFC9`, ₩9,900) issues an **annual** key with `expiresAt`. Signature Edition (`GROBLE_SIGNATURE_PRODUCT_IDS`, default `8Xy27f`, ₩29,000) issues a **lifetime** key with `edition: 'signature'`, `updatesUntil` (end of the KST day three years after purchase) and `support`. `updatesUntil` is a promise only. The app does not lock when it passes. Basic (`GROBLE_BASIC_PRODUCT_IDS`, `id:months` entries, default `SfYBy5:1,vdw3HN:12`; ₩3,900 a month or ₩39,000 a year) issues a **monthly** or **annual** subscription key with `edition: 'pro'`, `productId` and `billingCycleMonths`. Hama (`GROBLE_HAMA_PRODUCT_IDS`, default `R3n8zG:1,atqjpJ:12`; ₩12,900 a month or ₩139,000 a year) issues the same kind of key with `edition: 'hama'` and enrolls it in the [Hama plan](#hama-plan). Only an active Basic or Hama key, or a key with an active Hama plan, gets hosted Rau-0.1. Records without `expiresAt` (old one-time, Signature, beta, grandfathered and manual keys) are lifetime. A lifetime key is Signature only when `edition` is `signature`. Event names and fields follow [Groble's event reference](https://groble.im/help/guides/webhook-events).

- `POST /v1/groble/webhook` receives Groble events (register `https://rau-credits-production.up.railway.app/v1/groble/webhook` in Groble 내 스토어 → 연동, events `payment.completed`, `payment.cancel_requested`, `payment.refunded`, `subscription_payment.completed`, `subscription_payment.refunded`, `subscription_payment.failed`, `subscription.cancel_requested`, `subscription.terminated`). It checks `X-Groble-Signature` (or `X-Groble-Signature-Previous`) = HEX(HMAC-SHA256(secret, `${X-Groble-Timestamp}.${rawBody}`)) in constant time against `GROBLE_WEBHOOK_SECRET` and `GROBLE_WEBHOOK_SECRET_PREVIOUS`, rejects timestamps more than 5 minutes off, and dedupes on `X-Groble-Idempotency-Key`.
  - `payment.completed` issues one key per `merchantUid` after checking the product id and that product's own price. Yearly and the paused one-time product expect `GROBLE_EXPECTED_PRICE` (default 9900) and `GROBLE_MIN_AMOUNT`. Signature expects `GROBLE_SIGNATURE_EXPECTED_PRICE` (default 29000) and `GROBLE_SIGNATURE_MIN_AMOUNT`. Basic expects `GROBLE_BASIC_MONTHLY_PRICE` (3900) or `GROBLE_BASIC_YEARLY_PRICE` (39000) by its months, with `GROBLE_BASIC_MONTHLY_MIN_AMOUNT` and `GROBLE_BASIC_YEARLY_MIN_AMOUNT`. Hama expects `GROBLE_HAMA_MONTHLY_PRICE` (12900) or `GROBLE_HAMA_YEARLY_PRICE` (139000), with `GROBLE_HAMA_MONTHLY_MIN_AMOUNT` and `GROBLE_HAMA_YEARLY_MIN_AMOUNT`. Basic and Hama are subscription products, so a `payment.completed` for one is held as `wrong_product`. `GROBLE_PRODUCT_PRICES` (`id:price` or `id:price:min`) overrides one row. A Signature payment at ₩29,000 is accepted. The same amount on `uRshdR` or `GLJFC9` is held as `wrong_price`. An order that fails a check is **held** (no key) for `orders --status held` and `release`. Releasing a held Signature or Hama order stamps its edition.
  - `payment.cancel_requested` is recorded only. `payment.refunded` revokes on a full refund (or when partial refunds add up to the paid amount) and records partial refunds. A refund that arrives before its completion means no key is ever issued.
  - `subscription_payment.completed` with `billingReason: INITIAL` issues one key per `merchantUid` (same product and price checks, `paymentType == SUBSCRIPTION`) with `expiresAt` = the end of the KST day `billingCycleMonths` (default 12) after the payment. A Basic or Hama product always runs on its configured months: a missing or unreadable `billingCycleMonths` uses them, and an event whose `billingCycleMonths` names another cycle is held as `cycle_mismatch` (initial and renewal rounds), so a monthly buyer never gets a year. Its `sellerReference` links the subscription to the key. `RENEWAL` finds that key by `sellerReference` (else the one live subscription key with the buyer's email) and extends it by the key's own cycle (one month for a monthly key) from its current expiry, or from the day it was paid if it lapsed (a late retry or re-payment starts a new year on its payment day). Each round's `merchantUid` is recorded, so a replay never extends twice. A renewal checks product and currency only, so a later price change never holds old subscribers. An unmatched renewal is held: `extend` the key (a held renewal cannot be `release`d).
  - `subscription_payment.failed` puts the key in `past_due` and keeps it **fully usable past `expiresAt`** through Groble's retry and grace window (3 daily attempts, then 7 days; groble.im/legal/refund 제6조 제13항): until `failure.gracePeriodEndsAt` when the event carries it (the final attempt does), else `expiresAt` + `GROBLE_PAYMENT_GRACE_DAYS` (default 10), and never more than `GROBLE_PAYMENT_GRACE_MAX_DAYS` (default 14) past `expiresAt`, so a monthly key cannot run another month unpaid. `subscription.terminated` or the window's end stops it; a paid retry renews as usual and clears it.
  - `subscription.cancel_requested` and `subscription.terminated` are recorded on the key (`subscription.status` `cancel_requested` / `terminated`, `autoRenew: false`). They never shorten the paid year: an immediate termination (`SELLER_CANCELLED`, `CONTENT_DELETED`) still runs to `expiresAt`. `subscription_payment.refunded` takes back the refunded round's time, and revokes once every paid round of the key is refunded.
  - Unknown event types, events with no `merchantUid` and subscription events with no matching key answer 200 (so Groble stops retrying) and are recorded as held in `webhook-log.json`.
  - Every held order and every such event is emailed to `management@heemangstudios.com` (`held-alert.mjs`, same Resend key and layout as the rejection alert): the reason in Korean, buyer email, amount, `merchantUid` and KST time, never headers, signatures or the body. One email per order or event, with no time window across orders; a replay or re-delivery of the same order and reason is not mailed again (Resend idempotency key `held-<merchantUid>-<reason>`).
  - Replies (Groble retries 408/429/5xx for about 44 hours and treats other 4xx as final; it never gets 3xx or 410):

    | Status | `error` | Why |
    | --- | --- | --- |
    | 200 | | Handled, held or ignored |
    | 503 | `not_configured`, `missing_headers`, `bad_timestamp`, `bad_signature`, `body_too_large` | The signature could not be checked or did not match. Groble keeps retrying while the secret or setup is fixed |
    | 401 | `timestamp_out_of_window` | Signed, but more than 5 minutes off. Replay protection, final |
    | 400 | `json_invalid`, `payload_invalid` | Signed, but the body is unreadable. Final |
    | 500 | `store_error` | Saving failed. Groble retries |
    | 429 | `rate_limited` | More than 30 rejections per IP (300 overall) in 10 minutes. Not recorded |

  - Every rejected webhook and every held order is recorded in `webhook-log.json` (newest 200) with the time, reason, status, whether the signature matched, the request headers without `X-Groble-Signature*`, `Authorization` or `Cookie`, `X-Groble-Timestamp`, `X-Groble-Idempotency-Key`, and the event type, id and `merchantUid` when the body is JSON. For an unverified request those body fields are whatever the sender claimed. Held entries also keep the outcome (`action`), buyer email and amount, and `ackedAt` once the owner dismisses them.
  - Every rejection also emails `management@heemangstudios.com` through Resend after the reply, at most once per reason per 15 minutes; the next email for that reason counts the ones in between. It carries the reason, time and status only. Without `RESEND_API_KEY` the alert is skipped with a log line.
- `GET /v1/groble/webhook` answers 200 when the webhook secret is set and 503 when it is not. The deploy workflow polls it.
- `GET /v1/license/by-ref?ref=` returns `{status:'pending'}`, `{status:'issued', key, licenseExpiresAt}` (epoch ms, `null` for lifetime) or `{status:'revoked'}` for the success page. A Signature key also includes `edition`, `prioritySupport` and `updatesUntil` (epoch ms); a Basic or Hama key includes `edition` (`basic` or `hama`) and `plan`. No buyer data. CORS echoes only `LICENSE_ALLOWED_ORIGINS`. 120 requests per minute per IP.
- `POST /v1/license/activate {key, deviceId, appVersion, platform}`, `POST /v1/license/validate {key, deviceId}`, `POST /v1/license/deactivate {key, deviceId}`. Two devices per paid key; beta keys carry their own limit. Success: `{ok:true, lease, keyId, tier ('paid'|'beta'), expiresAt (lease end, epoch ms), licenseExpiresAt (key end, epoch ms, null = lifetime), autoRenew (null for lifetime), licenseState ('active' | 'payment_failed'), paymentGraceEndsAt (epoch ms while payment_failed, else null), paymentFixUrl (annual keys only: Groble's buyer page where the payment is fixed), devicesUsed, deviceLimit}`. A Signature key adds `edition: 'signature'`, `prioritySupport` and `updatesUntil` (epoch ms) on this JSON only. They are not inside the signed lease, so an old app keeps unlocking a lifetime key and a passed update promise cannot lock the app. Every success also carries `plan` (`monthly`|`annual`|`lifetime`) and `rau: {eligible}` (true for an active Basic or Hama key, including its payment grace, and for a key with an active Hama plan), and a Basic or Hama key adds `edition`. All of these are additions; older apps ignore them. Errors: `{ok:false, error}` with `invalid_key` (404), `revoked` (403, with `tier`), `expired` (403, an annual key past `expiresAt` and any payment grace, with `tier`, `licenseExpiresAt` and `paymentFixUrl`; deactivate still works), `device_limit` (409), `not_activated` (404, validate on a device that never activated), `device_id_invalid` (400), `server_not_configured` (503).
- Basic was called Pro until 2026-10-31. Keys stored as `pro` read as `basic` and are not rewritten. Only an app that sends `X-Hama-Plan-Names: basic` hears `edition: 'basic'` and `rau_requires_basic`; every other client (shipped apps, the website) still hears `pro` and `rau_requires_pro`.
- A lease is `payload.signature`: `payload = base64url(JSON {v:1, kid, keyId, keyHash, deviceId, issuedAt, expiresAt[, licenseExpiresAt]})`, where `licenseExpiresAt` appears only for annual keys so lifetime leases are unchanged, and `signature = base64url(Ed25519 over the ASCII payload segment)`. Times are epoch ms, valid 7 days (3 days for beta keys). `kid` is `LICENSE_SIGNING_KEY_ID` (default `hama-prod-1`). `keyHash` is hex SHA-256 of the key as the app sent it, trimmed, uppercased and without whitespace, so the app's own normalization of its stored key matches. `license-lease.mjs` `verifyLease(lease, {kid: publicKey}, {deviceId, key})` mirrors the app's check and only needs `node:crypto`. `GET /v1/license/public-key` returns `{alg, kid, rawBase64, spkiDerBase64}`; the app pins `rawBase64` under `kid`.
- `POST /v1/license/grandfather {installId}` returns a free key, once per install, when `sha256(installId)` is in `unique-installs.json` with `os` in `GRANDFATHER_PLATFORMS` (default `darwin`) and `firstSeenAt` before `GRANDFATHER_CUTOFF`. Without the cutoff it answers `grandfather_disabled`.
- Admin (`Authorization: Bearer $ADMIN_TOKEN`): `GET /v1/admin/licenses?key=|keyId=|merchantUid=|email=|ref=`, `GET /v1/admin/orders?status=held|issued|refunded&contentId=`, `GET /v1/admin/webhooks?kind=rejected|held&limit=50`, `GET /v1/admin/licenses/betas`, `GET /v1/admin/licenses/signatures` (Signature buyers: email, key, `updatesUntil`, status), `GET /v1/admin/licenses/customers` (paid keys newest first with `subscriptionStatus` `active`|`past_due`|`lapsed`|`lifetime`, devices and email delivery), `GET /v1/admin/attention` (held orders not yet handled plus held webhook events that hold no order, both until acknowledged), and `POST /v1/admin/licenses/{issue,issue-beta,revoke,restore,reset-devices,remove-device,resend-email,extend}`, `POST /v1/admin/orders/{release,apply-renewal}` and `POST /v1/admin/attention/ack`. `remove-device {keyId|key, deviceId}` frees one device and keeps the others (`device_not_found` 404). `apply-renewal {merchantUid, keyId|key}` applies a held renewal round to the buyer's annual key exactly like a matched webhook (one cycle from its expiry, the round recorded for refunds, the renewal email queued) and links the round's ref to that key. `attention/ack {id}` dismisses a held webhook event and `{merchantUid}` a held order the owner will not release; a newly held round shows again. License views and customers carry `plan` (`monthly`|`annual`|`lifetime`; Basic and Hama views add `billingCycleMonths`), `expiresAt`, `subscription`, `extensions`, `prioritySupport` and, for Signature, `edition`, `productId`, `updatesUntil`, `support` and `supportSlaLabel`. `scripts/license-admin.mjs` wraps them:

  After fixing a `bad_signature` or `not_configured` alert, Groble's retries issue the keys on their own. A final rejection (401/400) never comes back: find its `merchantUid` with `webhooks --rejected`, take the buyer email from Groble and run `issue --merchant-uid ... --email ... --send-email`.

  Beta-tester keys (`beta`, `POST /v1/admin/licenses/issue-beta {name, email?, devices?, note?}`) work like paid keys on macOS and Windows but allow `devices` simultaneous devices (default 5, clamped to 1..50) and get 3-day leases, so a `revoke` locks an online app at its next daily check and an offline one within 3 days. They are never emailed: `beta` prints the key on its last line. `betas` lists each key with its tester, status, devices (platform, last seen) and revocation time. Records without `tier` or `deviceLimit` are paid keys on two devices.

  For the same calls in a browser, run `npm --prefix site-api run admin-ui` and open http://127.0.0.1:8790 (`--port` or `PORT` to change). A red 확인할 주문 band at the top lists held orders (키 발급 releases one; a held renewal picks the buyer's key and 연장 applies it) and held events (확인 dismisses them, persisted server-side); the wall display shows the same count in red. The 제보 inbox lists issue reports (unread ones lit) and shows the message, meta, screenshot, log, chat and document downloads, 답장 by email, 해결 and 삭제; opening a report marks it seen. The 고객 table lists paid keys with term, devices (빼기 frees one), email delivery, 다시 보내기 (optionally to a corrected address), 1년 연장 and 해지/복구, and its form issues and emails a 1-year key. It also creates, lists, revokes, restores and resets beta keys, sets each beta key's gift credit (크레딧 column), and looks up any key by key or email. It listens on 127.0.0.1 only and forwards a fixed set of admin routes to `SITE_API_BASE` (default production) with the token added server-side. The token comes from `ADMIN_TOKEN`, else the macOS Keychain item `hamaeditor-license-admin`, which the page fills in once if both are missing. Requests need this server's `Host`, a per-launch session token from the page and no foreign `Origin`. To open it from another tailnet device, put `tailscale serve` in front and set `ADMIN_UI_PUBLIC_ORIGIN=https://<ts.net name>:<port>`; it stays bound to 127.0.0.1.

  A manual key with a `merchantUid` is reused if the Groble webhook for that order arrives later, and a later refund webhook still revokes it. `issue --years N` (or `--until DATE`) makes the manual key an annual key, for a subscription order whose webhook never arrived. `issue --edition signature` makes a Signature key (no `expiresAt`). `--years` together with `--edition signature` is `term_conflict`. `--updates-until YYYY-MM-DD` sets the update promise to the end of that KST day. The default promise is three years from now. `extend` adds N years (default 1) to an annual key from its expiry, or from now if it lapsed; `--until YYYY-MM-DD` sets the end of that KST day. Lifetime keys answer `lifetime_key`. Each extension is kept in the key's `extensions`.
- Key email goes out after the webhook reply through Resend (`RESEND_API_KEY`, `LICENSE_EMAIL_FROM`). Without the API key the attempt is logged and marked `skipped`; the webhook still succeeds and the success page still shows the key. Failed sends retry up to 3 times, including after a restart. Every email is built on `email-layout.mjs` (banner, key card, download button, footer); its images live in `website/assets/email/` on GitHub Pages, and the deploy workflow waits for them to go live before it deploys the server. The key email's copy follows why it went out: a purchase or released hold, a subscription renewal, a Signature purchase, an admin `resend-email`, or an admin `issue --send-email` with no payment behind it. Subscription keys get one line under the key card with the next renewal date (매달 or 매년, or the end date once auto-renewal is off). Basic mail names Basic, Rau-0.1 and two devices; Hama mail adds the Hama agent. A monthly key's renewal sends no key email; Groble sends the receipt. Signature mail names Signature and 우선 지원 · 1영업일, and puts the update-promise date under the card. The card itself holds only the key. A lifetime key that is not Signature gets no date. Support stays email-only at `management@heemangstudios.com`.

### Gift credits (SPECIAL EVENT)

A one-time gift of Claude usage for Pi (`GIFT_AMOUNT_USD` unless the key has its own amount), one per beta license key (`tier: 'beta'`, shared by its devices) on macOS and Windows. Paid and grandfathered keys do not get it. The app authenticates with its license lease as `Authorization: Bearer <lease>`; the server checks its own signature, expiry, that the license is active, that the lease's device is still activated, and the key hash. Anything else is `unauthorized` (401). A valid lease is `not_eligible` unless the key is a beta key and the device's `platform` is in `GIFT_PLATFORMS`; this is checked on every status, claim and proxy call.

- `GET /v1/gift/status` → `{ok, event:{id, amountUsd, endsAt, active}, eligible, claimed, remainingUsd, usedUsd, claimedAt}`. `event.amountUsd` is this license's amount: its key's limit once claimed, else its allocation, else `GIFT_AMOUNT_USD`. An unclaimed key allocated $0 is `eligible: false`. Balances come from the key's `limit_remaining` on OpenRouter (BYOK spend plus OpenRouter fees), cached 15 s, and are `null` when it does not answer.
- `POST /v1/gift/claim` (body `{}`) is idempotent. The first call creates one OpenRouter key named `hama-gift-<event>-<keyId>` with `limit` = the license's amount and `include_byok_in_limit: true`, and keeps the key in `gifts.json`; it is never sent to the app. Errors: `unauthorized` 401, `not_eligible` 403 (also for a $0 allocation), `event_inactive` 410 (event not configured or past `GIFT_ENDS_AT`), `budget_exhausted` 409 (the created limits would pass `GIFT_TOTAL_BUDGET_USD`), `upstream_unavailable` 502. A claim interrupted after OpenRouter created the key leaves a `provisioning` record; the next claim deletes keys with that name before creating a new one.
- OpenAI-compatible proxy at `/v1/gift/openrouter` (Pi `baseUrl`, lease in place of the API key). Errors use OpenRouter's `{error:{code,message}}` shape: 401 `unauthorized`, 403 `not_eligible` or `gift_not_claimed`, 410 `event_inactive`, 402 `Insufficient credits: ...` once the key limit is spent or the gift is disabled.
  - `POST /chat/completions` streams SSE through as it arrives, and a client disconnect aborts the upstream request. Models must start with one of `GIFT_MODEL_PREFIXES` (also every entry of `models`); `max_tokens`/`max_completion_tokens` are clamped to `GIFT_MAX_OUTPUT_TOKENS` and `max_tokens` is set when neither is given. Bodies up to 16 MiB, 4 concurrent requests and 60 per minute per license.
  - `GET /models` is the OpenRouter catalog filtered to the allowed prefixes, cached 10 minutes. `GET /auth/key` (and `/key`) and `GET /credits` answer OpenRouter-shaped balances for the gift.
- Admin: `GET /v1/admin/gifts?status=&eventId=` lists grants without their keys plus `committedUsd` and `allocations`; `POST /v1/admin/gifts/disable {keyId, reason}` disables the OpenRouter key (`PATCH /keys/{hash} {disabled:true}`) and marks the grant `revoked`. A revoked license loses the gift at once because its lease no longer authenticates.
- Per-key amounts: `POST /v1/admin/gifts/amount {keyId, amountUsd}` (beta keys only, 0–1000, rounded to cents) stores `allocations[keyId]` for the current event. On a claimed key it first sets the OpenRouter limit (`PATCH /keys/{hash} {limit}`) and then `limitUsd`; lowering below what was spent leaves the gift used up, and $0 is refused by the proxy itself. A raise must fit `GIFT_TOTAL_BUDGET_USD` (`budget_exhausted` 409); while a change is on its way, or after a PATCH that failed without a clear answer, it stays counted as `pendingLimitUsd`. A revoked gift only stores the amount. Errors: `amount_invalid` 400, `invalid_key` 404, `gift_provisioning` 409 (claim in progress), `upstream_unavailable` 502. `POST /v1/admin/licenses/issue-beta` also takes `giftUsd`, and `GET /v1/admin/licenses/betas` adds `giftEvent` and each key's `gift: {amountUsd, status: unclaimed|provisioning|active|revoked, limitUsd, usedUsd, remainingUsd, claimedAt}` (`null` without an event; balances from the 15 s cache, `null` when OpenRouter does not answer).

```sh
node scripts/license-admin.mjs gifts [--status active]
node scripts/license-admin.mjs gift-disable --key-id lic_... --reason abuse
node scripts/license-admin.mjs gift-amount --key-id lic_... --usd 30
node scripts/license-admin.mjs beta --name "홍길동" --gift-usd 10
```

OpenRouter → Settings → Integrations → Anthropic: add the Anthropic Console API key as a BYOK key in the **Prioritized** section, and set **Shared capacity fallback** to "Never use shared capacity for any model on this provider". Without that, a rate-limited or failing Anthropic key falls back to OpenRouter credits.
2. Keep a small OpenRouter credit balance. BYOK requests cost 5% of the normal OpenRouter price from OpenRouter credits, after a monthly fee-free allowance ($25,000 of list-price usage on pay-as-you-go). A gift key's limit counts both the Anthropic spend and that fee.
3. Create a management key at openrouter.ai/settings/management-keys and set it as `OPENROUTER_PROVISIONING_KEY`. If it has an expiration, replace the variable before that date; an expired key makes claims fail with `upstream_unavailable`.

Every response on these routes leaves the gift's OpenRouter key out: the claim, status and proxy answers build their own bodies, and admin views drop `openrouterKey`.

### Hama plan

A hosted plan: the app's Pi harness runs through this server, metered per license key against a monthly USD allowance with rolling caps. It is off unless `HAMA_ENABLED=true`; every `/v1/hama/*` and `/v1/admin/hama*` route answers 404 until then. The pool is tentative, so every number is an env variable. Eligibility is an active plan in `hama.json`: Basic, beta and every other edition never grant Hama, so an active lease that is not enrolled gets 403 `hama_not_enrolled` on status and on both proxy routes.

A plan comes from one of two places:

- **A Groble purchase.** A paid Hama product issues a key with `edition: 'hama'` and writes its plan right after the webhook, with the default allowance and `periodAnchor` = the first payment. Renewals keep the plan and its ledger. A cancel request, a termination or a failed renewal changes nothing until the key's own end: the plan runs to `expiresAt`, plus the payment grace while the renewal is past due, exactly like a Basic key. Then it is `disabled` with `disabledReason: 'subscription_ended'`. A refund that revokes the key ends it at once. A late renewal, an `extend` or a `restore` brings it back with the same anchor and ledger.
- **An admin enrollment** of any key (below). Subscription events never touch these plans.

Access never depends on the stored status keeping up. An ended key's lease stops authenticating on the next call, and a live Hama key without a plan writes it on its next call, which covers a released hold, a crash right after the webhook, or a key bought while `HAMA_ENABLED` was off. Admin routes bring `hama.json` up to date before they answer. An admin `disable` (`disabledReason: 'admin'`) holds against renewals until the admin enrolls the key again; it does not take Rau away from a Hama key, because Rau follows the key's edition. Revoke the key to end both.

The app authenticates with its license lease (same check as the gift) as `Authorization: Bearer <lease>` or `x-api-key: <lease>`. Errors: 401 `unauthorized`, 403 `hama_not_enrolled` (valid lease, no active plan).

- Models: the only hosted Claude model is `anthropic/claude-haiku-5.5` (Anthropic `claude-haiku-5-5`), a constant in `hama.mjs`. No env or flag adds Sonnet or Opus, and `HAMA_CHEAP_MODELS` refuses Claude ids. Cheap fallback models come from `HAMA_CHEAP_MODELS`.
- Caps, as percentages of the key's allowance: `cap_5h` (spend in the trailing 5 hours, `HAMA_CAP_5H_PCT`), `cap_week` (trailing 7 days, `HAMA_CAP_WEEK_PCT`) and `cap_month` (the current billing month, `HAMA_CAP_MONTH_PCT`). Billing months start on `periodAnchor`'s day and time (UTC) each month, clamped to short months (Jan 31 → Feb 28/29 → Mar 31). A call is admitted while every applicable window is under its cap, so the last call may overshoot by its own cost. Claude is held by all three caps, cheap models only by `cap_month`; all spend counts in all windows. `resetsAt` is when the window drops back under its cap (`null` while under it; the period end for `cap_month`); with several caps blocking, the one that frees up last is reported.
- Accounting (`hama-ledger.mjs`, pure): spend per minute for 5 hours, per hour for 7 days, and a running total per billing period. A bucket counts as if its spend happened at its end, so a window may over-count by one bucket and never under-counts. Each call is recorded once by its provider id (message or generation id); the last 500 ids of the last 24 hours are kept, so a repeated report, also after a restart, is not billed twice.
- `GET /v1/hama/status` → `{ok, plan:{status, allowanceUsd, periodStart, periodEnd}, caps:{cap_5h|cap_week|cap_month:{usedUsd, limitUsd, resetsAt}}, blocked: null | {cap, resetsAt, cheapAvailable}, models:{default, claude, cheap, maxOutputTokens}, endpoints:{anthropic, openai}}`. 120 per IP per minute.
- Proxy (`hama-proxy.mjs`), lease as the API key. Both routes stream SSE through as it arrives, a client disconnect aborts the upstream call, bodies are capped at 16 MiB, and each license gets 4 concurrent requests and 60 per minute (429 `rate_limited`). Errors use the route's native shape: Anthropic `{type:'error', error:{type, message}}`, OpenAI `{error:{code, message}}`, with 401 `unauthorized`, 403 `hama_not_enrolled`, 400 `model_not_allowed`/`tool_not_allowed`, 503 `not_configured` (no upstream key) and 502 `upstream_unavailable`.
  - `POST /v1/hama/anthropic/v1/messages` (Pi `anthropic-messages`, `baseUrl = <site>/v1/hama/anthropic`): model `anthropic/claude-haiku-5.5` or `claude-haiku-5-5` only. `max_tokens` is clamped to `HAMA_MAX_OUTPUT_TOKENS` (set when missing); server tools and `mcp_servers` are refused because they bill outside token usage. Client auth headers are dropped; only `anthropic-version` (default `2023-06-01`) and `anthropic-beta` are forwarded. It goes to Anthropic (`ANTHROPIC_API_BASE/v1/messages`, `x-api-key: ANTHROPIC_API_KEY`) first, and to OpenRouter's Anthropic-compatible `POST {OPENROUTER_API_BASE}/messages` with `HAMA_OPENROUTER_KEY` and model `anthropic/claude-haiku-5.5` only before any byte reached the client, on a network error or timeout, 429, 5xx (529 overloaded included), 401/402/403, a 400 about the credit balance, or a 200 stream whose first event is an overloaded/api/rate-limit error. Any other 4xx passes through. A session that failed over stays on OpenRouter for 30 minutes (prompt caches are per provider).
  - `POST /v1/hama/openrouter/chat/completions` (Pi `openai-completions`, `baseUrl = <site>/v1/hama/openrouter`): `HAMA_CHEAP_MODELS` only (also every entry of `models`; Claude ids are refused), sent with the selected `reasoning.effort` (`low`, `high`, or `max`; omitted effort uses `HAMA_CHEAP_REASONING_EFFORT`), clamped `max_tokens`/`max_completion_tokens`, `usage: {include: true}` and `stream_options.include_usage`. The OpenRouter provider that served a session's first call is put first for its later calls (`provider: {order: [it], allow_fallbacks: true}`), and `session_id` is set for OpenRouter's own sticky routing. `GET /models` lists the cheap models.
  - Sessions: Pi's `x-session-id` (or `prompt_cache_key`) when sent, else a hash of the key, model, system prompt and first user message; kept in memory, 5,000 sessions for up to an hour.
  - Billing: usage is read from the stream as it passes, without holding bytes back, and each call is recorded once by its message or generation id. Cost is OpenRouter's reported `usage.cost` when present (`costSource: upstream`), else the Haiku price table (`price_table`). A stream cut before its final usage (client disconnect, upstream drop) is still billed: reported input plus at least 1 output token per 3 bytes of streamed text, or 1 input token per 3 request bytes when nothing was reported (`estimate`).
- Owner setup: create `HAMA_OPENROUTER_KEY` with a hard credit limit on OpenRouter. OpenRouter BYOK is per account, so if that account routes Anthropic through the BYOK key from the gift setup with shared capacity off, the Claude backup reaches the same Anthropic key and fails with it. Keep the Hama key in an account (or workspace) without that BYOK rule so the backup is real.
- Admin (`ADMIN_TOKEN`): `GET /v1/admin/hama?status=` lists plans with their caps and totals; `POST /v1/admin/hama/enroll {keyId, allowanceUsd?, periodAnchor?}` enrolls an existing license or re-activates and updates its plan (`allowanceUsd` 0–1000 overrides `HAMA_MONTHLY_ALLOWANCE_USD`, `null` goes back to it; `periodAnchor` defaults to the enrollment time and is kept on later calls); `POST /v1/admin/hama/disable {keyId}` ends access and keeps the ledger, and plan views carry `disabledReason`; `GET /v1/admin/hama/usage?keyId=&limit=` returns the plan and its newest usage log entries (100 by default, at most 1000). Errors: `invalid_key` 404 (no such license), `hama_not_found` 404, `allowance_invalid` 400, `period_anchor_invalid` 400.

### Hosted Rau-0.1 (Basic and Hama)

Rau-0.1, the taste learner in `rhwp/rhwp-agent/taste-learner.mjs`, runs on this server for active Basic and Hama keys and active Hama plans, so the app never calls OpenRouter or any provider with a key. The app authenticates with its lease (`Authorization: Bearer <lease>`, the same check as gifts). A Basic key qualifies until its expiry and payment grace end. A Hama key qualifies the same way, on its edition, also with `HAMA_ENABLED` off. Any other key with an active plan in `hama.json` qualifies while the license itself is live; with `HAMA_ENABLED` off no plan counts. Every other key (GLJFC9, lifetime, Signature, beta, grandfathered, manual, a Basic key past its expiry and payment grace, or revoked) gets `rau_requires_pro`, a code kept for the apps already shipped; a lease that is not ours, expired, or for a removed device is `unauthorized`.

- `POST /v1/rau/learn {prompt}`: `prompt` is a non-empty string of at most 48 KB UTF-8. The server sends it as one user message to `RAU_MODEL` (default `deepseek/deepseek-v4.1-flash`, a pinned id, never the `~` alias) with `reasoning: {effort: RAU_REASONING_EFFORT}` (default `low`), `max_tokens` = `RAU_MAX_OUTPUT_TOKENS` (default 2000), not streamed, and answers `200 {ok:true, text, model, usage:{usedUsd, capUsd, remainingUsd, resetsAt}}`. `text` is the model's reply as is.
- `GET /v1/rau/status` → `{ok:true, eligible, reason (null|'rau_requires_basic'), upgradeUrl, capUsd, usedUsd, remainingUsd, resetsAt}`. `capUsd` is the license's plan cap, or the Basic cap when not eligible; `usedUsd` and `remainingUsd` are `null` when not eligible. It never creates an OpenRouter key.
- Errors are `{ok:false, error, ...}`: 400 `invalid` with `field` (`prompt` or `body`), 401 `unauthorized`, 403 `rau_requires_basic` with `upgradeUrl` (`BASIC_UPGRADE_URL`), 402 `rau_cap_reached` with the plan's `capUsd`, `usedUsd` and `resetsAt`, 429 `rate_limited` with `Retry-After` (2 concurrent and 20 per minute per license, 120 per minute per IP), 502 `upstream_unavailable`, 503 `rau_not_configured` (no `OPENROUTER_PROVISIONING_KEY`, or `RAU_ENABLED=false`).
- Caps: a hard USD limit per UTC calendar month, `RAU_MONTHLY_CAP_USD_BASIC` (default 2.00) for Basic and `RAU_MONTHLY_CAP_USD_HAMA` (default 5.00) for Hama. A Hama key and a license with both plans get the Hama cap. License answers (`/v1/license/activate`, `/v1/license/validate`) report `rau.eligible` by the same rule.
- Allowance: the first learn call creates one OpenRouter key per license, `hama-rau-<keyId>`, with `limit` = the license's cap, `limit_reset: 'monthly'` (OpenRouter resets at 00:00 UTC on the 1st) and `include_byok_in_limit: true`. The period is the UTC calendar month and `resetsAt` the next 1st at 00:00Z. When the stored period or cap differs from the current one, the next call PATCHes the key once with the cap and the monthly reset, so a changed cap or plan takes effect and a reset OpenRouter skipped is asked for again. If that PATCH failed and the key's lower old limit refuses a call under the raised cap, the call answers `upstream_unavailable` and the next one retries the PATCH. Before each call the server refuses once this month's spend reaches the cap, taking the higher of OpenRouter's count (`GET /key`, cached 15 s) and its own ledger of each response's `usage.cost`. An upstream key-limit refusal (402/403) also answers `rau_cap_reached` and fills the ledger. Two calls at once can each pass the check, so a month can end at most two calls over the cap; the OpenRouter limit still holds. The key stays in `rau.json` and is never in any response.
- `GET /v1/admin/rau` (`ADMIN_TOKEN`) lists allowances without their keys, with each one's `capUsd`, this month's `usedUsd` and `remainingUsd`, plus the model, period and `capsUsd: {pro, hama}`. `node scripts/license-admin.mjs rau` prints one line per license.

At about $0.0003 a call on the default model, the $2 cap is roughly 6,600 calls a month and the $5 cap roughly 16,600.

Keys look like `HAMA-XXXXX-XXXXX-XXXXX-XXXXX-XXXXX` (125 random bits, Crockford base32). The server assumes **one replica**: all license writes go through one in-process lock and an atomic temp-file rename.

### Accounts

HamaEditor accounts sign in with WorkOS AuthKit (email magic link on the AuthKit page, or Google) through the system browser and a loopback callback in the app. `accounts.mjs` owns accounts, devices and sessions; `workos.mjs` is the only outbound call (10 s timeouts). The plan follows the account's linked licenses, and the app gets an account lease (v2) instead of a license lease. Every `/v1/account/*` route answers `503 accounts_not_configured` until `WORKOS_API_KEY` (and the license signing key, which signs the account lease) is set. They are app routes: no CORS. Errors are `{ok:false, error, ...extra}`.

- `GET /v1/account/auth/providers` → `{ok, providers}` from `ACCOUNT_AUTH_PROVIDERS`. `email` is AuthKit's own page (`provider=authkit`, with `login_hint` when given), `google` `GoogleOAuth`. Any other id fails startup.
- `POST /v1/account/auth/start {provider, challenge, port, state, loginHint?}` → `{ok, url, expiresAt}`: `challenge` is base64url(SHA-256(PKCE verifier)), `port` the app's loopback port (1024–65535), `state` the app's nonce (`[A-Za-z0-9_-]{16,128}`). The login lives 10 minutes; `url` is the WorkOS authorize URL with the login id as `state`. Errors: 400 `invalid` with `field`, 400 `provider_unavailable`, 429 `rate_limited` (20 per IP per 10 minutes).
- `GET /v1/account/auth/callback` is the WorkOS redirect target. It takes the login (single use), exchanges the code with `WORKOS_API_KEY`, finds the account by WorkOS user, else by verified email, else creates one, and answers 302 to `http://127.0.0.1:<port>/auth/callback?code=<grant>&state=<app state>`. A WorkOS error answers the same URL with `error=auth_cancelled` (`access_denied`) or `auth_failed`. An unknown or expired login gets a one-line Korean page and no redirect. Codes, grants, sessions and full emails are never logged. A verified email then links that email's licenses to the account.
- `POST /v1/account/auth/token {code, verifier, device:{id, name, platform, appVersion}, replaceDeviceId?}` → `{ok, session, ...account}`. The grant is single use, bound to the PKCE challenge, valid 10 minutes and 10 attempts; every failure is 400 `grant_invalid`. An account holds `ACCOUNT_DEVICE_LIMIT` devices; the same device id signing in again replaces its session and keeps its slot. At the limit it answers 409 `device_limit {limit, devices}` (the grant stays), and a retry with `replaceDeviceId` removes that device and its session first (404 `device_not_found` for another id). 30 per IP per 10 minutes.
- Session routes take `Authorization: Bearer hes_...`. A session is per device, stored only as its SHA-256, and is invalid (401 `session_invalid`) once its device is removed, it signed out, the account is gone, or it was not used for 180 days. `POST /v1/account/refresh {appVersion?}` → the account payload with a fresh lease; it marks the device seen (at most once an hour) and links licenses of a verified email bought since. `POST /v1/account/signout` removes this device and is idempotent. `POST /v1/account/devices/remove {deviceId}` → `{ok, signedOut:false, devices}`, or `{ok, signedOut:true}` for the calling device; 404 `device_not_found`.
- `POST /v1/account/redeem {key}` links a key the user typed (any spacing or case; the `HAMA-` prefix is optional) → `{ok, alreadyLinked, license, ...account}`, where `license` is the key as `licenses` lists it. Errors: 400 `invalid_format`, 404 `invalid_key`, 403 `revoked`, 409 `key_linked_elsewhere`. 20 per account per hour (429 `rate_limited`, failures count).
- `POST /v1/account/claim {orderId, email}` links the key of a Groble order bought with another email: `orderId` is the Groble order number (`merchantUid`) and `email` the buyer email on that order (any case). Same answer as redeem. An unknown order, a wrong email or an order without a key is 404 `order_not_found` (one code, so neither can be probed); a held order is 409 `order_not_ready`; also 403 `revoked` and 409 `key_linked_elsewhere`. 10 per account per hour.
- `POST /v1/account/profile {name}` → `{ok, account}`. 1–30 characters, no control characters (400 `name_invalid`). A name the user set is never replaced by a later sign-in.
- `PUT /v1/account/avatar` with the picture as the raw body (`Content-Type` `image/jpeg`, `image/png` or `image/webp`, at most 1 MiB) → `{ok, avatar:{rev, type, bytes}}`. The first bytes must match the type. Errors: 413 `too_large` (a body declared past 2 MiB is refused unread), 415 `unsupported_type`, 429 `rate_limited` (30 per account per hour). It is stored as `avatars/<accountId>.<ext>` (temp file and rename, mode 0600) and `rev` goes up by one on every upload, also after a removal. `GET /v1/account/avatar` → the bytes with `Content-Type`, `ETag: "<rev>"` (304 for a matching `If-None-Match`) and `Cache-Control: private, no-cache`; 404 `no_avatar`. `POST /v1/account/avatar/remove` → `{ok}`.
- `POST /v1/account/stats {batchId, agentSessions, documentsEdited}` → `{ok, stats}` adds the app's activity counts (integers 0–1000; `batchId` `[A-Za-z0-9_-]{8,64}`). A batch id among the account's last 50 is a no-op, so a retried flush counts once. 400 `invalid` with `field`.
- `POST /v1/account/delete {confirm}` → `{ok}`. `confirm` is the account email (any case; 400 `confirm_mismatch`). While a linked key is live and auto-renewing (`subscription.autoRenew` not false and not terminated) it answers 409 `subscription_active {manageUrl}` (`GROBLE_PAYMENT_FIX_URL`) and changes nothing; a cancel request, a terminated subscription, a lifetime key or a gift key does not block. Then, without holding both locks: the keys are unlinked (`unlinkedBy: 'delete'`, so the same email links them to a new account), the account with its devices, sessions, picture and stats is removed, and the WorkOS user is deleted best effort (a failure is logged and the answer is still 200). Hama ledgers stay on their license keys.
- The account payload: `account {id, email, name, avatar, provider, createdAt}`, `plan {tier, keyId, edition, plan, expiresAt, autoRenew, paymentFailed, paymentGraceEndsAt, manageUrl, rau:{eligible}}`, `licenses` (masked keys, primary first), `devices` (newest first, `current` marks the caller), `deviceLimit`, `stats {agentSessions, documentsEdited, since, hama}`, `lease` and `leaseExpiresAt`. `stats.hama` is `{usedUsd, allowanceUsd, periodEndsAt, calls}` for the current billing period of the account's Hama key (the key Hama itself would use), and `null` without an active plan or with `HAMA_ENABLED` off. Times are epoch ms except `account.createdAt` (ISO).
- Tier: a linked license is live while active and before its expiry plus payment grace (lifetime keys always). Rank 3 is a Hama key or a key with an active Hama plan (`tier: 'hama'`), 2 a Pro key (`pro`), 1 any other key (`legacy`); no live license is `free`. The primary license is the highest rank, then the latest end, then the oldest.
- Licenses link on the license record (`accountId`, `linkedAt`, `linkedBy`): every non-revoked key bought with the account's **verified** email (`email`), a Groble purchase whose buyer email belongs to a verified account at once (`purchase`), a redeemed key (`redeem`), a claimed order (`claim`), a redeemed gift code (`gift_code`) and an admin link (`admin`). An unverified email links nothing, and a key an admin unlinked is never linked back by email.
- Account lease: `payload.signature` like the license lease, same key and `kid`, payload `{v:2, kid, accountId, deviceId, keyId (primary or null), tier, plan, issuedAt, expiresAt[, licenseExpiresAt][, paymentGraceEndsAt]}`, valid 7 days (3 when the primary key is a beta key). `license-lease.mjs` `signAccountLease` and `verifyAccountLease(lease, keys, {deviceId, accountId})` (reasons as `verifyLease`, with `wrong_account`); each version's verifier rejects the other. Gifts, Hama and Rau accept both: a v1 lease authenticates as before, and a v2 lease needs its account and a live session on its device, then picks the license for the service now: a live beta key for the gift, a key with an active Hama plan or the Hama edition for Hama, the best Rau plan for Rau, else the primary. Rau answers `rau_requires_pro` to a free account; the others answer 401.
- Admin: `GET /v1/admin/accounts?email=|id=|keyId=` → `{ok, accounts}` with devices, stats and linked licenses (never sessions or grants). `POST /v1/admin/accounts/unlink {keyId}` → `{ok, changed, license}` frees a key from its account; `POST /v1/admin/accounts/link {keyId, accountId}` → `{ok, previousAccountId, license}` links it to an existing account (`account_not_found` 404), moving it from any other. License views carry `accountId`, `linkedBy`, `linkedAt` and `unlinkedAt`.

```sh
node scripts/license-admin.mjs accounts --email user@example.com   # or --id acct_... | --key-id lic_...; last lines: <id> <email> · 기기 N · 키 <keyId> <status>
node scripts/license-admin.mjs account-unlink --key-id lic_...
node scripts/license-admin.mjs account-link --key-id lic_... --account-id acct_...
```

### Gift codes

An admin issues a batch of codes; a signed-in user redeems one for a Basic or Hama key of a fixed term, linked to their account. The issue and redeem logic is in `licenses.mjs` (redeeming a code and creating its key is one mutation of `licenses.json`), the code format in `gift-codes.mjs`.

- Codes are `GIFT-XXXX-XXXX-XXXX-XXXX`: 16 Crockford base32 characters, 80 random bits. Input is normalized like a license key (case, spaces, dashes, a missing `GIFT-` prefix, O → 0, I/L → 1). The server stores only the SHA-256 of the normalized code and its first group (`GIFT-XXXX`); the plaintext is in the issue answer and nowhere else, never in logs, lists or `licenses.json`.
- `POST /v1/admin/gift-codes/issue {plan, durationMonths | durationDays, count, note?, redeemBy?}` (`ADMIN_TOKEN`) → `{ok, batch, codes}`. `plan` is `basic` or `hama` and the term exactly one of `durationMonths` (1–120) or `durationDays` (1–3660); neither has a default. `count` is 1–1000. `redeemBy` (`YYYY-MM-DD` = end of that KST day, or ISO-8601, in the future) is the last moment a code can be redeemed. Errors (400): `plan_required`, `plan_invalid`, `duration_required`, `duration_conflict`, `duration_invalid`, `count_invalid`, `redeem_by_invalid`; 403 `forbidden`.
- `GET /v1/admin/gift-codes?batchId=&status=` → `{ok, count, batches}`, newest first. Each batch has its fields, `counts {active, redeemed, revoked, expired}` and `codes` (filtered by `status`): `{codeHash, maskedCode, status, createdAt, redeemedAt, accountId, keyId, revokedAt}`. `codeHash` is the stored SHA-256, an opaque id that cannot give the code back. `expired` is an unredeemed code past its batch's `redeemBy`. 400 `status_invalid`.
- `POST /v1/admin/gift-codes/revoke {batchId | code | codeHash, reason?}` → `{ok, changed, batch}` revokes unredeemed codes: every one of a batch, or one code by its plaintext or its listed `codeHash`. A redeemed code is 409 `code_redeemed {keyId}`; revoke its key with `/v1/admin/licenses/revoke` instead. Errors: 400 `target_required` (not exactly one target), 400 `invalid_format`, 404 `invalid_code`, 404 `batch_not_found`.
- `POST /v1/account/gift-codes/redeem {code}` (account session) → `{ok, alreadyRedeemed, license, ...account}`, like `/v1/account/redeem`. The new key is `{source: 'gift_code', edition: plan, expiresAt, giftBatchId}`, linked with `linkedBy: 'gift_code'`. Its term starts at redemption: `durationMonths` ends like a subscription round (end of the KST day that many calendar months later), `durationDays` at the end of the KST day that many days later. The same account again gets `alreadyRedeemed: true` and the same key. Errors: 400 `invalid_format`, 404 `invalid_code`, 409 `code_redeemed` (another account), 410 `code_revoked`, 410 `code_expired` (past `redeemBy`), 401 `session_invalid`, 429 `rate_limited` (10 per account per hour, failures count), 503 `accounts_not_configured`.
- A gift key is a Basic or Hama key for every entitlement: account tier, primary license, hosted Rau, and with `HAMA_ENABLED` a Hama plan from the same subscription sync as a paid Hama key (run right after the redeem, anchored at redemption). It never renews: `plan: null` and `autoRenew: false` in the account payload, its `licenses` entry and the license lease, `manageUrl: null`, no `paymentFixUrl`, no key email, and it never blocks account deletion. At `expiresAt` it lapses like any key; an admin can `extend` or `revoke` it like any key.

```sh
node scripts/license-admin.mjs gift-codes issue --plan basic|hama --months N | --days N --count N [--note "..."] [--redeem-by YYYY-MM-DD] [--out codes.csv]
node scripts/license-admin.mjs gift-codes list [--batch-id gcb_...] [--status active|redeemed|revoked|expired]
node scripts/license-admin.mjs gift-codes revoke --batch-id gcb_... | --code GIFT-... [--reason "..."]
```

`issue` prints the codes once, one per line after the JSON. With `--out` they go only to that file (CSV `code,batch_id,plan,duration_months,duration_days,redeem_by`, mode 0600, created before the request and never overwritten), and stdout shows the batch without them. Nothing else ever prints a code.

Storage (two flat maps in `licenses.json`, one table each later):

- `giftCodeBatches: { [batchId]: { batchId, plan, durationMonths | durationDays, count, note?, redeemBy?, createdAt } }`, `batchId` = `gcb_` + 18 hex.
- `giftCodes: { [codeHash]: { codeHash, batchId, prefix, status: 'active'|'redeemed'|'revoked', createdAt, redeemedAt?, accountId?, keyId?, revokedAt?, revokeReason? } }`. `expired` is derived from the batch's `redeemBy`, never stored.

Open owner calls, deliberately not decided in code: which plan and term each batch grants (both required, no defaults); whether existing keys stay lifetime and any cutoff for key-only (v1) activation, which gift codes do not change; and whether a code whose account was deleted may be redeemed again by a new account (today it answers 409 `code_redeemed`; `account-link` moves the freed key by hand).

## Run and deploy

```sh
npm test
npm start          # http://127.0.0.1:5180
```

Production is the Railway project `rau-credits`, service `rau-credits` (`https://rau-credits-production.up.railway.app`), with a volume mounted at `/data`. Deploys go through the GitHub Actions workflow below. Keep the service's GitHub source disconnected (Railway → rau-credits → Settings → Source) so a merge deploys once. For a manual deploy, link this directory once with `railway link` and run `railway up` from `site-api/`. `railway.toml` sets the start command and the `/healthz` health check.

Before a Signature test buy, set these Railway variables on `rau-credits` (the code defaults match, and the Groble product `8Xy27f` stays a draft until Finance starts the sale):

```
GROBLE_SIGNATURE_PRODUCT_IDS=8Xy27f
GROBLE_SIGNATURE_EXPECTED_PRICE=29000
GROBLE_SIGNATURE_MIN_AMOUNT=29000
```

Leave `GROBLE_SUBSCRIPTION_PRODUCT_IDS=GLJFC9` and `GROBLE_EXPECTED_PRICE=9900`. Leave `GROBLE_ONETIME_PRODUCT_IDS=uRshdR` so old refunds still resolve. Do not start the Groble sale from this repo.

On main, `.github/workflows/site-api-deploy.yml` does this automatically for any change under `site-api/`: it runs the tests, runs `railway up site-api --path-as-root --service rau-credits --environment production --ci` with the `RAILWAY_TOKEN` repository secret (a Railway **project** token for the production environment), then waits up to 10 minutes for `GET /v1/groble/webhook` to answer 200 (404 = the old deployment is still live, 503 = webhook secret missing) and checks that `/v1/license/public-key` answers 200 (503 = signing key missing). Roll back with Railway → service → Deployments → previous deployment → Redeploy; `licenses.json` on the volume is untouched by a rollback.
